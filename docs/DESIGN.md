## 1. 产品概述

### 1.1 一句话定义

一个常驻后台的 Windows 语音输入工具。说出唤醒词后，你讲的话会实时出现在**任意应用**的光标处。

### 1.2 核心价值

把「打字」换成「说话」，但不改变你现有的工作流——它不要求你在某个特定软件里工作，文字直接进你正在用的那个程序。

### 1.3 与现有方案的差异

| 方案 | 局限 |
|---|---|
| 系统自带语音输入 | 需按住热键、唤醒词不可自定义、无结束词与自动发送 |
| 云端听写服务 | 需联网、麦克风音频上传云端 |
| **本产品** | 完全本地、语音唤醒、结束词与发送键可配、注入任意应用 |

### 1.4 项目性质与演进路线

自用优先，同时作为完整工程实践的载体。据此分两阶段演进：

- **阶段一（本文档范围）**：单机桌面版，把核心体验和系统层难点做扎实
- **阶段二**：引入服务端，支持词表同步与团队共享

这条演进路径会影响若干接口设计，见 §3.4。

## 2. 核心交互

### 2.1 状态机

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    听到唤醒词     ┌───────────┐          │
   │  IDLE   │ ───────────────▶ │ LISTENING │          │
   │ 待唤醒  │                  │   听写中  │          │
   └─────────┘                  └───────────┘          │
        ▲                             │                │
        │                             │ 结束词 / 静音超时 / 切窗口
        │                             ▼                │
        │                       ┌───────────┐          │
        └───────────────────────│ COMMITTING│──────────┘
                                │   提交中  │
                                └───────────┘
```

任何时刻只处于且仅处于一个状态。该状态机是整个程序的骨架，必须显式建模。

**非法事件一律忽略并记录，不抛异常。** 真实场景里迟到事件是常态：引擎在 COMMITTING
阶段还会吐出最后一个中间结果、静音计时可能与结束词同时到达、窗口监听可能重复触发。
状态机的职责是吃掉这些。

### 2.2 一次完整使用

1. 程序常驻后台，桌面上只有一颗悬浮球，显示「待唤醒」
2. 你在任意应用里，把光标放到想输入文字的位置
3. 说「**子曰**」→ 悬浮球变为「听写中」，浮窗出现在光标附近
4. 正常说话，文字**实时出现在浮窗里**（此时目标程序完全不受影响）
5. 说「**到此为止**」，或静音 5 秒 → 浮窗文字经精化后**一次性注入**光标处
6. 若开启了自动发送，再模拟一次按键（Enter / Ctrl+Enter）
7. 回到「待唤醒」，等待下一次

> 任何时刻按 **Esc** 可取消整段，一个字都不会打出去。

### 2.3 完整交互清单

产品**没有主窗口**，所有操作都从悬浮球（或托盘图标）发起，或由语音触发。

| 动作 | 触发方式 | 前置状态 | 结果 |
|---|---|---|---|
| 开始听写 | 说唤醒词「子曰」 | IDLE | → LISTENING，浮窗出现 |
| 开始听写 | 悬浮球左键 | IDLE | 同上（不喊唤醒词的备用路径） |
| 结束本段 | 说结束词「到此为止」 | LISTENING | → COMMITTING |
| 结束本段 | 悬浮球左键 | LISTENING | → COMMITTING |
| 结束本段 | 静音满 N 秒 | LISTENING | → COMMITTING |
| 结束本段 | 前台窗口变化 | LISTENING | → COMMITTING，**但放弃注入**（见 §7） |
| 取消本段 | Esc | LISTENING / COMMITTING | → IDLE，本段丢弃，一个字都不注入 |
| 暂停 / 恢复监听 | 菜单「暂停监听 / 恢复监听」 | 任意 | 悬浮球变暗+斜杠；忽略唤醒词与结束词 |
| 打开设置 | 菜单「设置...」 | 任意 | 打开设置窗口的「常规」页 |
| 查看日志 | 菜单「查看日志」 | 任意 | 打开设置窗口的「日志」页 |
| 移动悬浮球 | 拖动 | 任意 | 位置改变，夹在屏幕内 |
| 贴边收起 | 拖到屏幕左右边缘 40px 内松手 | 任意 | 吸附到该侧，只露 20px |
| 滑出 / 收回 | 鼠标移到露出部分 / 移开 | 已收起 | 自动滑出、约 450ms 后收回 |
| 退出程序 | 菜单「退出」 | 任意 | 结束进程 |

## 3. 功能范围

### 3.1 MVP

| # | 功能 | 要点 |
|---|---|---|
| 1 | 常驻悬浮球 + 托盘图标 | 悬浮球颜色即状态，可拖到左右边缘贴边收起；托盘图标为二级入口。二者共用右键菜单 |
| 2 | 配置文件 | JSON：唤醒词、结束词、静音时长、发送键、自动发送开关、悬浮球位置；启动时**强制校验** |
| 3 | 音频采集 | 单路 `TargetDataLine`，16kHz/16bit/单声道，分发给唤醒检测与预览识别 |
| 4 | 状态机 | IDLE / LISTENING / COMMITTING，显式建模，非法事件忽略并记录 |
| 5 | 语音唤醒 | 小 Vosk 受限语法检测唤醒词；词不在模型词表内则启动失败并提示 |
| 6 | 实时预览 | 小 Vosk 流式识别，文字实时出现在浮窗（不抢焦点）；Esc 整段取消 |
| 7 | **转写精化** | 段落结束时用 **SenseVoice** 重跑该段音频，取得更准且**带标点**的最终文本（原定 whisper.cpp；当前实现为 Vosk 离线重跑，见 `ENGINE-EXPERIMENT.md`） |
| 8 | 结束检测 | 结束词 / 静音超时（默认 5 秒后结束录制，可调可关）/ 切窗口 |
| 9 | 文本注入 | `SendInput` + `KEYEVENTF_UNICODE`；**注入前校验前台窗口**；失败须明确提示 |
| 10 | 自动发送 | 触发时机与按键可配，默认**关闭** |
| 11 | 标点 | **SenseVoice 原生标点为主力**（`use_itn=1`）；预览阶段辅以停顿启发式。`PunctuationProcessor` 职责下调为「数字规整与清理」，不再是标点主力（TECH-PLAN §5.3） |
| 12 | 日志 | 状态流转 + 错误，滚动 5MB×3，**不记转写内容** |
| 13 | 打包 | jpackage 产出 exe |

### 3.2 明确不做

热词表、多词表切换、历史记录、云端同步、全局热键、多语言、跨平台、开机自启动。

### 3.3 后续规划

| 阶段 | 内容 | 说明 |
|---|---|---|
| 二 | **热词表（外部来源）** | 可插拔的词表来源，提升专业术语识别率与后处理纠错。重点在外部来源机制 |
| 二 | **更大模型** | 若转写质量仍不理想，换用更大的 whisper 或 vosk-model-cn-0.22 |
| 三 | **服务端** | 词表云端同步、团队共享、增量下发 |

### 3.4 接口伏笔

以下接口是产品演进的主要接缝。`TextRefiner` 在 MVP 内即实现，其余先留位置，将来均为纯增量扩展：

| 接口 | MVP 实现 | 后续扩展 |
|---|---|---|
| `TextRefiner` | `TextRefiners.SenseVoice`（sherpa-onnx）——**当前因原生产物不可得而降级为 `TextRefiners.VoskOffline`**，见 `ENGINE-EXPERIMENT.md` | 更大模型 / 云端引擎 |
| `CommitPolicy` | `WholeSegmentPolicy`（整段注入） | `StablePrefixPolicy`（稳定前缀增量注入） |
| `TextPostProcessor` | `PunctuationProcessor`（职责下调：数字规整与清理，**不是标点主力**） | `HotwordCorrector`（热词纠错） |
| `HotwordSource` | 暂不实现 | 本地文件 / 插件目录 / 远端服务 |

此外，热词表 JSON 格式中预留 `version` 字段，供阶段三的增量同步使用。

## 4. 系统架构

### 4.1 处理管线

```
                    ┌──────────────────────────┐
   麦克风 ─────────▶ │  音频采集（单路）         │
                    │  16kHz / 16bit / 单声道  │
                    └────────────┬─────────────┘
                                 │ 分发
              ┌──────────────────┴──────────────────┐
              ▼                                     ▼
   ┌────────────────────┐              ┌────────────────────┐
   │ 唤醒 / 结束词检测   │              │ 实时预览            │
   │ 小 Vosk · 受限语法  │              │ 小 Vosk · 流式      │
   └─────────┬──────────┘              └─────────┬──────────┘
             │ 命中                              │ 增量文本
             ▼                                   ▼
   ┌────────────────────┐              ┌────────────────────┐
   │      状态机         │◀────────────▶│     浮窗预览        │
   └─────────┬──────────┘              └────────────────────┘
             │ 段落结束
             ▼
   ┌──────────────────────────┐
   │ 音频缓存（当前段 PCM）     │
   └────────────┬─────────────┘
                ▼
   ┌──────────────────────────┐
   │ SenseVoice 精化           │  更准 + 原生标点
   └────────────┬─────────────┘
                ▼
   ┌──────────────────────────┐
   │ 文本注入 / 自动发送        │  SendInput + KEYEVENTF_UNICODE
   └──────────────────────────┘
```

单进程、全本地、不依赖网络。

### 4.2 双引擎分工（核心架构决策）

| 职责 | 引擎 | 理由 |
|---|---|---|
| 唤醒词 / 结束词检测 | **小 Vosk**（42MB，受限语法） | 它是**唯一支持运行时动态词表**的；且只需检测少数几个词，准确率劣势不影响 |
| 实时预览 | **小 Vosk**（流式） | 只有它提供流式输出，能让字边说边长 |
| 实际转写 | **SenseVoice**（原定 whisper.cpp） | 纯 CPU 快一个数量级，且原生带标点；因段落结束才跑，非流式不构成问题 |

> ⚠️ **实现现状（见 `ENGINE-EXPERIMENT.md`）**：`TECH-PLAN` §1.1 定的方案 C
> 是精化引擎换成 SenseVoice（sherpa-onnx），但**sherpa-onnx 没有 Maven Central 的
> Java 绑定、也没有 Windows x64 预编译产物**，因此 MVP 的精化位当前装的是
> `TextRefiners.VoskOffline`（Vosk 整段离线重跑），并**如实标注为「非 SenseVoice」**。
> `TextRefiner` 接口、状态机、UI、注入路径一行未改——这就是 §3.4 留这个接口的价值。
>
> **时机**：`TextRefiner` 在 §3.4 被列为「MVP 内即实现」的接缝，它的**位置**确实实现了；
> 但**实现体**（SenseVoice）被原生产物卡住，属已知缺口，不是设计变更。

**为什么转写引擎的选型标准里必须有「纯 CPU 速度」这一维**：
Step 0（附录 B.2）只在**准确率**这一个维度上比较过 Vosk 与 whisper，
得出「whisper 更准且带标点」的结论。但 Step 0 **没有测 whisper 在纯 CPU 上多慢**——
实测数据（`TECH-PLAN` §4.2）显示 whisper-small 处理 5 秒音频需 12–15 秒，
与 §6 的「提交延迟 < 2.5s」差一个数量级。本次实现又实测到：
即便是小得多的 **Vosk 小模型，纯 CPU 也要 1.21 秒/5 秒音频**（RTF 0.241）。
这从侧面印证了 whisper-small 的推算量级是合理的，也说明
**转写引擎的选型必须同时看准确率与纯 CPU 速度**，只看准确率会得出不可用的结论。

该分工由 Step 0 的准确率数据 + `TECH-PLAN` §4 的速度数据共同确定，依据见附录 B 与 B.4。

### 4.3 关键设计约束

- **麦克风只开一路。** 唤醒检测与预览识别共用同一个 `TargetDataLine`，由采集线程分发。禁止各自开设备——Windows 上会互相抢设备，且时序对不齐。
- **注入器按「批」设计。** 接口收整段字符串，内部决定如何分批调用 `SendInput`。整段注入用一次，未来增量注入用多次，调用方无感。
- **字符计数用码点。** 涉及「第几个字符」的下标一律用 `codePointCount`，避免代理对导致退格数算错。
- **浮窗不得抢焦点。** 必须 `WS_EX_NOACTIVATE`，且窗口变化事件中显式忽略自身句柄，否则会自我触发「切窗口结束」。
- **配置必须显式校验。** Vosk 对词表外的词是**静默忽略**的，不能依赖引擎报错。见附录 C。

### 4.4 UI 设计

**UI 表面**（注意：这个产品**没有主窗口**，用户永远不会「打开」它）

启动后桌面上只有一颗**悬浮球**，它是产品的主要入口与状态指示。设置窗口按需打开，关掉不等于退出。

| 界面 | 出现频率 | 说明 |
|---|---|---|
| **悬浮球** | 常驻 | **主要入口**。左键手动听写 / 右键菜单 / 拖动移位 / 拖到左右边缘贴边收起；颜色即状态（灰=待唤醒、红+脉冲=听写中、橙=提交中、暗灰+斜杠=已暂停） |
| **浮窗预览条** | 每次说话 | 产品的脸，需要认真打磨 |
| **设置窗口** | 极低频 | 从菜单进入。页签：常规（配置）/ 日志 |
| **托盘图标** | 常驻 | 二级入口，与悬浮球共用同一套菜单。⚠️ **Windows 11 默认把它收进「隐藏的图标」折叠面板**，用户需手动拖出来一次才常驻 —— 因此不能把它当作唯一的兜底入口 |
| 错误提示气泡 | 偶发 | 注入失败等**静默失败必须可见** |
| 词表校验提示 | 改配置时 | 放在设置窗口的常规页，否则用户会陷入「改了没反应」 |

悬浮球与托盘图标共用菜单：手动开始/结束听写 · 暂停监听 · 设置... · 查看日志 · 退出。

**悬浮球规范**

- **不得抢焦点**，理由与浮窗预览条相同（见下）。
- **贴边收起**：拖到屏幕左右边缘 40px 以内松手，即吸附到该侧并收起，只留 20px 在屏幕内；鼠标移到露出部分滑出，移开约 450ms 后收回。
  - ⚠️ 几何关系容易算错：悬浮球窗口是 68px，但球体只占中间 52px（外圈是留给听写脉冲动画的留白）。所以「露出 20px 窗口」实际只露出约 12px 的**球体**。按球体边缘算，不要按窗口算。
  - ⚠️ **收起状态必须用轮询，不能依赖 `mouseEntered`。** 实测：窗口只有 20px 在屏幕内时鼠标事件不会送达（原型自检中 `mouseEntered` 计数为 0）。轮询仅在贴边期间运行、150ms 一次，开销可忽略。
- **拖动必须夹在屏幕范围内**：即使有托盘图标兜底，把球拖到屏幕外也会让人找不到它。
- 位置与贴边状态需持久化到配置（原型尚未实现）。

**技术选型：Swing / AWT**

| 方案 | 结论 |
|---|---|
| **Swing / AWT** | **采用**。JDK 自带零依赖；`JWindow` 直接暴露底层 HWND，用 JNA 设 Win32 扩展样式（`WS_EX_NOACTIVATE` 等）最自然 |
| JavaFX | 不采用。其优势（CSS / FXML / 动画 / 控件库）在本产品上基本用不上；而 `Stage` 封装了 HWND，拿它做置顶不抢焦点的小窗反而要绕路 |
| 内嵌 WebView | 不采用。为一个只显示文字的浮窗背一个 Chromium，不成比例 |
| 纯 Win32 窗口 | 不采用。文字渲染、圆角、阴影全要手绘，工作量不成比例 |

**浮窗规范** —— 这是最容易做错、做错则产品直接废掉的部分

- 必须带 `WS_EX_NOACTIVATE`（不抢焦点）与 `WS_EX_TOOLWINDOW`（不进 Alt+Tab 与任务栏），且**必须在窗口显示之前设置**，否则会先闪一下焦点再还回去。Swing 侧对应 `setFocusableWindowState(false)` 与 `setAutoRequestFocus(false)`。
- 窗口变化事件中**必须显式忽略浮窗自身句柄**，否则浮窗弹出会被判定成「用户切窗口」，当场结束这一段。
- 定位降级链：光标坐标 → 目标窗口矩形 → 跟随鼠标。`GetCaretPos` 在 Chrome / Electron 中经常取不到。
- 屏幕边缘翻转：右侧越界向左翻，下方越界向上翻。
- 视觉：半透明圆角 + 两级文字样式（已稳定 / 仍在变）+ 状态行；字号跟随系统 DPI。

**已由原型验证的两个风险点**（`demo/` 用 `java.awt.Robot` 驱动真实鼠标事件，`--ui-test`）

1. **`JPopupMenu` 能否从「不抢焦点」的窗口弹出** —— 能，通过。这本是个真实风险：菜单可能弹不出来或弹出来关不掉。
2. **贴边收起状态下的鼠标事件** —— **收不到**，因此改为轮询（见上）。

**自动化 UI 自检的两条前提**（都是踩过坑才明白的）

- **绝不能在 EDT 上跑。** `Robot.delay` 阻塞的是当前线程；若那就是 EDT，Robot 产生的鼠标事件与 Swing 的动画 Timer 都排不进队，断言会全部失真 —— 表现为「明明点了却没反应」。
- **坐标一律用 AWT 逻辑坐标，不要自己乘 DPI 缩放。** `Robot.mouseMove`、`MouseInfo.getPointerInfo()` 与 `Window.getBounds()` 处在同一个坐标空间（都带缩放）。手动乘一次缩放系数会把坐标推到屏幕外并被夹到边缘，点到完全无关的地方。

> 这两条对**真实实现**同样成立：将来用 Win32 `GetCaretPos` 拿光标位置、用
> `SendInput` 注入文字时，Win32 用的是**物理像素**，而 Java 是**逻辑像素**，
> 中间必须显式换算。这是本项目最容易反复踩的一个坑。

### 4.5 代码组织（建议）

```
talkinglive/
├── App.java              装配与启动（唯一有 main 的类）
├── core/
│   ├── StateMachine.java      状态机（纯逻辑，可单测）
```

## 5. 关键技术决策

| 决策项 | 选择 | 理由 | 备选 |
|---|---|---|---|
| 交付形态 | 单机 Windows 桌面软件 | 自用优先，无需服务端 | Electron 外壳 |

| 触发条件 | 结束词 / 静音 / 切窗口 | 覆盖提前结束、忘记说结束词、中途离开三种情况 | 仅结束词 |

| UI 工具包 | Swing / AWT | 见 §4.4 | JavaFX；WebView |
| 打包 | jpackage | JDK 自带，产出带运行时的 exe | launch4j |
| 工具链 | JDK 21 + Maven | 两个引擎均有成熟的 Java 绑定；`jpackage` 免背 Chromium；构建与测试标准化。**注**：原写「虚拟线程契合音频与识别管线」——该理由不成立，全程序长期只有 3 根左右线程（TECH-PLAN §9 #7） | 现有 JDK 8 |

## 7. 异常与降级

**贯穿全篇的原则：任何失败都必须可见。** 这个产品常驻后台、平时没有界面，
静默失败会让用户完全无从判断——「我说了半天它没反应」是最糟的体验。

| 情况 | 表现 | 处理 |
|---|---|---|
| 无麦克风 / 设备被占用 | 启动时找不到可用设备 | 明确提示，程序仍常驻但置为不可用；不静默降级 |
| 采集中断（设备被抢占） | 音频流中断 | 记日志 + 悬浮球变暗 + 提示；尝试重连 |
| 模型缺失或损坏 | 启动加载失败 | 明确提示并给出获取方式（附录 D），**不静默失败** |
| 唤醒词 / 结束词不在词表 | 配置校验失败 | 拒绝该配置并提示，见附录 C |
| 目标程序以管理员运行 | 注入被 UIPI 静默丢弃 | 检测注入失败 → 提示需以管理员运行本程序 |
| 提交时前台窗口已变 | 注入会被误发到别的程序 | **放弃注入** + 明确提示；不自动发送 |
| 精化（SenseVoice）推理失败 / 超时 | 段落未精化 | 退回用 Vosk 预览文本注入，并记日志。已有实现与单测：`TextRefiner.Result.fallback` |
| 光标位置取不到 | 浮窗无法贴光标 | 降级链：目标窗口矩形 → 跟随鼠标 |
| 用户把球拖出屏幕 | 找不到球 | 位置夹在屏幕范围内 |
| 悬浮球被全屏程序遮挡 | 点不到球 | 托盘图标为二级入口（注意 Windows 11 会折叠它） |
| 单段录音过长 | 内存增长 | 达到上限自动结束本段（上限见 §12） |

## 8. 风险与未验证项

| 风险 | 说明 | 应对 |
|---|---|---|
| **自定义词不在词表内** | Vosk 对词表外词**静默忽略**（仅打 WARNING，不抛异常），配置会无声失效 | 启动时用 `vosk_model_find_word` 显式校验，失败则拒绝并提示 |
| **精化推理延迟**（原：whisper 推理延迟，风险已大幅下降） | 段落结束后需等待一次推理。原风险为 whisper-small 纯 CPU 约 12–15s（`TECH-PLAN` §4）；换 SenseVoice 后目标约 0.5s | 浮窗显示「处理中」；当前实现（Vosk 离线重跑）实测 RTF 0.241 守住 2.5s；**长段（>15s）会超预算**，靠单段上限 60s 与静音结束兜底 |
| **预览与最终文本不一致** | 预览来自小 Vosk（快但糙），最终来自 whisper（准） | 预览以弱化样式呈现，提交时整体替换 |
| **UIPI 权限隔离** | 目标程序若以管理员运行，注入会被静默丢弃 | 检测失败并提示；必要时以管理员运行本程序 |
| **光标定位不可得** | `GetCaretPos` 在 Chrome / Electron 中常取不到 | 降级路径：跟随目标窗口 / 跟随鼠标 |
| **误触发唤醒** | 看视频、开会时被误唤醒 | 选低误触发词；实测验证；提供一键暂停 |
| **ITN 会改字**（新） | SenseVoice 的 `use_itn=1` 不只是加标点，还会**规整数字**。官方英文样例中 `fifty pieces of gold` 被规整成 `50 pieces of code` | `AppConfig.itn` 开关已预留；接入后按 `TECH-PLAN` §6.3 实测中文场景是否可接受，再决定开/关/按场景 | Win32 用物理像素、Java 用逻辑像素，混用会打到完全错误的位置 | 全部换算集中在一处工具方法；已在原型里踩过一次（§4.4） |
| **引擎集成深度** | 识别引擎是第三方黑盒，不是自研代码 | 价值集中在集成层：低延迟、双引擎协同、流式修正处理 |

> ⚠️ **补充（TECH-PLAN §9 #13）**：Step 0 **只比较了准确率这一维**，
> **没有比较纯 CPU 速度**。而速度这一维后来成了架构决策的关键：
> whisper-small 纯 CPU 处理 5 秒音频约 12–15 秒（`TECH-PLAN` §4.2），
> 与 §6 的「提交延迟 < 2.5s」差一个数量级，于是才有了方案 C（精化引擎换 SenseVoice）。
> 本次实现又实测到：**即便小得多的 Vosk 小模型，纯 CPU 也要 1.21 秒/5 秒音频**（RTF 0.241），
> 侧面印证了那个推算的量级。教训：**引擎选型必须同时看准确率与纯 CPU 速度**。

## 附录 C：工程约束 — 词表的静默失效

### C.1 现象

传入词表外的词构建语法时，`KaldiRecognizer` **构建成功、不抛任何异常**，仅在 stderr 输出：

```
WARNING (VoskAPI:UpdateGrammarFst():recognizer.cc:308) Ignoring word missing in vocabulary: '本段结束'
```

后果：结束词永远不会被识别到，而用户与程序都毫无察觉。

### C.2 约束

1. **配置校验必须显式调用 `vosk_model_find_word`**，不能依赖引擎报错。校验失败要给出明确提示，而非静默降级。
2. **自定义词受模型词表限制。** 模型词表以「词」为单位（约 10 万条），多音节短语多数不是独立词条——`小助手`、`灵犀`、`到此为止` 在表内，而 `小秘书`、`小听写`、`本段结束` 不在。UI 侧必须校验并提示。

### C.3 待办

Step 0 的验证脚本目前位于 `%TEMP%\vosk-verify\`（`probe_vocab.py` / `probe2.py`）。项目骨架建立后，应将词表校验逻辑以单元测试形式固化进仓库——这是少数**不依赖麦克风、可纯单测**的引擎相关逻辑。

## 附录 D：模型获取

模型文件较大，**不进版本库**，统一放在：

```
%LOCALAPPDATA%\TalkingLive\models\
├── vosk-model-small-cn-0.22\      # 唤醒词/结束词检测 + 实时预览（约 42MB）
└── whisper\                        # 转写精化（模型待定，见 §12）
```

### D.1 Vosk 中文小模型

官方站点 `alphacephei.com` 在国内实测极慢（**约 40 KB/s**，42MB 需十几分钟）。
Hugging Face 镜像实测快约 87 倍（**约 3.5 MB/s**，12 秒下载完成）：

```
# 推荐：镜像（实测 3.5 MB/s）
https://hf-mirror.com/localstack/vosk-models/resolve/main/vosk-model-small-cn-0.22.zip

# 官方（作为备用）
https://alphacephei.com/vosk/models/vosk-model-small-cn-0.22.zip
```

解压后目录结构应为：

```
vosk-model-small-cn-0.22/
├── am/          声学模型
├── conf/
├── graph/       Gr.fst / HCLr.fst / phones/   ← 词表编在 FST 里，没有 words.txt
└── ivector/
```

> 注意：`graph/` 下**没有 `words.txt`**，词表被编译进 FST 二进制。所以查词必须用
> `vosk_model_find_word()` API，不能指望读文本词表。这是 Step 0 踩过的坑。

### D.2 精化模型（SenseVoice）

模型名已定：**`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`**，int8 量化。

```
# 模型（239 MB）与词表（316 KB）——hf-mirror 实测可下载
https://hf-mirror.com/csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17/resolve/main/model.int8.onnx
https://hf-mirror.com/csukuangfj/sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17/resolve/main/tokens.txt
```

放置位置：`%LOCALAPPDATA%\TalkingLive\models\sense-voice\`（`AppPaths.refinerModelDir()`）。

> ⚠️ **为什么现在还装不起来**：模型能下载，但 **sherpa-onnx 没有 Maven Central 的
> Java 绑定，也没有 Windows x64 预编译原生产物**。上游只发 Android/iOS/Python/C++ 产物，
> JVM 侧要使用者自己用 MSVC + CMake 构建 JNI 动态库——这与 `TECH-PLAN` §3.1
> 「零环境依赖」的红线冲突。
>
> 因此当前精化位由 **Vosk 整段离线重跑**顶替（实测 RTF 0.241，守住 §6 的 2.5s 预算）。
> 两条落地路径（onnxruntime 自写前处理 / 自编译 JNI）与取舍见
> `docs/ENGINE-EXPERIMENT.md` §4。
