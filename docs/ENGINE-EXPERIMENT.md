## 2. 前提核验：sherpa-onnx 与 SenseVoice 的可获取性

| 项 | 结论 | 依据 |
|---|---|---|
| `com.k2fsa.sherpa.onnx:*` 在 Maven Central | ❌ **不存在**（404） | 直接查仓库目录 |
| sherpa-onnx 官方 Java 绑定 | ⚠️ 存在于源码树 `sherpa-onnx/java-api/`，**但需自行构建**，且 JNI 层要自编译 | 官方文档「Non-Android Java」要求先 `cmake` 构建原生库 |
| Windows x64 预编译原生产物（jar 内） | ❌ **没有**（这是真正的阻塞点） | 上游只发 Android/iOS/Python/C++ 等产物；JVM 侧靠 JitPack 或本地构建 |
| JitPack 上的 sherpa-onnx | ✅ 可达（HTTP 200），但产物取决于上游构建脚本，**不保证含 Windows x64 DLL** | 不可作为 MVP 的可靠依赖 |
| SenseVoice ONNX 模型本身 | ✅ **可获取**：`model.int8.onnx` 239 MB + `tokens.txt` 316 KB，hf-mirror 实测可下载 | 见 §6 的下载地址 |

**判读**：模型侧没问题（239 MB int8 可下载），**问题全在 Java 绑定/原生产物这一侧**。
`sherpa-onnx` 的 JVM 支持要求使用者自己拿 C++ 工具链构建 JNI 动态库——
这与 `TECH-PLAN` §3.1「零环境依赖」的红线直接冲突（要求用户具备 MSVC + CMake 才能装这个软件）。

> 注意这条与 §5.4 的原判断有出入：原文写「二者理论上有 Windows x64 预编译产物，
> 无自编译 C++ 环节；**但需确认**」。**确认结果是没有**。

### 3.1 「合成音频」口径说明（重要）

上表的识别吞吐用的是**合成音频**（缓慢起伏的正弦），因此：
- **只反映解码算力开销**，不代表真实语音的识别质量、CER、标点质量。
- 合成音频没有真实的语音结构，解码器的搜索空间与真人说话不同，
  所以 RTF 只能当**数量级参考**，不能当准确曲线。

真实语音的 RTF 与 CER 需要**真人录音**，属 `DESIGN.md` §9.3 的手工验证，本环境无麦克风（见 §5）。

### 3.2 与 `TECH-PLAN` §4.2 推算的对照（这是本次最有价值的一条数据）

| 引擎 | 5 秒音频纯 CPU 耗时 | 来源 |
|---|---|---|
| whisper-small | 推算 **12–15 s** | `TECH-PLAN` §4.2（外部实测 + 内核折算） |
| **Vosk 小模型（本次实测）** | **1.21 s** | 本文 §3 |
| SenseVoice（目标） | 推算 **约 0.5 s** | `TECH-PLAN` §4.3（外部实测） |

**判读**：`TECH-PLAN` §4 关于「whisper 纯 CPU 不可行」的结论得到**侧面印证**——
即便是比 whisper-small 小得多的 Vosk 小模型，纯 CPU 也要 1.2 秒/5 秒音频；
whisper-small 比它大一到两个数量级，推算 12–15 秒是合理的。
但同时也说明：**当前回退方案（Vosk 离线重跑）能守住 §6 的 2.5s 预算**，
不需要破 `TECH-PLAN` §3.1 的「不依赖核显」红线。

## 4. 方案 C 的落地路径（待办）

`sherpa-onnx` 不可直接依赖，因此精化的替代路径有两条，**都需要决策**：

### 路径 1：改用 onnxruntime + 自写 SenseVoice 前处理（推荐）

- 依赖 `com.microsoft.onnxruntime:onnxruntime`（**Maven Central 有，且带 Windows x64 原生库**）
- 自己实现：80 维 log-mel 滤波器组（10ms 帧移）→ `model.int8.onnx` 推理 → CTC 贪心解码 → `tokens.txt` 解码
- 优点：零自编译、纯 CPU、与方案 C 的目标一致（RTF ≈ 0.1）
- 成本：前处理与解码要自己写并验证（这是 §6 那半天的实验内容）
- **风险**：SenseVoice 的 ITN 与标点是与模型绑定的后处理，自写解码需确认能拿到同样效果

### 路径 2：自编译 sherpa-onnx JNI

- 优点：直接用官方 API
- 缺点：**要求使用者装 MSVC + CMake**，与「零环境依赖」红线冲突；分发体积也大
- 结论：**不推荐**，除非将来愿意把原生产物随包分发（那就变成了构建流水线的活）

**接口接入成本**：两条路径都只需新增一个 `TextRefiner` 实现并把
`App.createRefiner` 指向它。`TextRefiner` 接口、状态机、`CommitPolicy`、
注入路径、UI **全部无需改动**——`TECH-PLAN` §5.1「替换点只有一处」在本仓库里
**已经被代码结构证明**（见 `src/main/java/com/talkinglive/App.java` 的 `createRefiner`）。

## 4.5 实测发现的准确率上限：模型能力，不是代码问题

**现场证据**（诊断模式 `-Dtalkinglive.log.text=true` 的真实日志）：

```
gen=1  预览『那天天气不是很好到此为止』      精化『那天天气不是很好到此为止』      差异=0码点
gen=2  预览『明日放走好名字房租吧』          精化『明日放走好名字房租把刀子的』    差异=4码点
gen=3  预览『现在一麦克风测试现在进行卖空测试』精化『…』                        差异=4码点
```

两条结论：

1. **预览与精化错得一样。** 两者都基于同一个 `vosk-model-small-cn-0.22`
   （CER **17.15%**），只是解码路径不同，所以精化**几乎没有纠错能力**——
   这正是 TECH-PLAN §6.5 判读规则 #2 警告过的情况（「精化后并不比预览好，
   精化这一步失去意义」）。实测证据就是「与预览差异=0码点」。
2. **错误是识别错误，不是后处理问题。** 注入的文本已与识别结果一致
   （文本层只做了必要的唤醒词/结束词剔除），所以「麦克风→麦克风/卖空」
   这类错字**只能靠换更准的模型解决**。

### 已实现的解法：识别统一走一个模型（**自动生效，无需配置**）

`AppPaths.asrModelDir()` 按「显式配置 > 自动探测大模型 > 小模型」决定**识别用模型**，
而**实时预览、落字、段落精化三者共用它**。`AppPaths.detectLargeModelDir()` 会在
`%LOCALAPPDATA%\TalkingLive\models\` 下自动探测 `vosk-model-cn-0.22` 或 `model-cn`
（两个名字都认：官方解压名与我们下载脚本的解压名）。**只要目录在就自动用**。

| 职责 | 模型 | 原因 |
|---|---|---|
| 唤醒词 / 结束词检测 | **必须**用小模型 | 只有它支持运行时动态词表（附录 B.2；实测 `graph/` 下无 `Hclg.fst`，故能按语法重建解码图）。大模型词表静态，实测 C 层输出 `Runtime graphs are not supported by this model` |
| 实时预览 + 落字 + 段落精化 | 同一个（优先大模型） | 三者必须给出**同一句话**，见下方「为什么必须共用」 |

仍可用系统属性 / 环境变量**显式指定**识别模型（优先级最高）：

```powershell
java -Dtalkinglive.model.asr="D:\some\other\model" -jar target\talkinglive.jar
$env:TALKINGLIVE_ASR_MODEL = "D:\some\other\model"
```

#### 为什么预览与落字必须共用同一个模型（实测数据）

拿同一段合成语音「现在是人工智能输入测试，今天天气不错」对比两个模型：

| | 小模型 `vosk-model-small-cn-0.22` | 大模型 `vosk-model-cn-0.22` |
|---|---|---|
| 识别结果 | 现在是人工智能**收入**测试今天天气不错 | 现在是人工智能**输入**测试今天天气不错 |
| 英文词表 | **完全没有**（A–Z、AI、APP、CPU、PDF、PPT… 全部 `find_word` 返回 -1） | 有（`AI`=4245、`APP`=6917、`CPU`=27073…） |

更长的一段（13.6 秒）差距更明显：

| | 小模型 | 大模型 |
|---|---|---|
| 结果 | …**挺拔**我说的话准确的写出来不要**肉质**也不要**多次** | …**请把**我说的话**准确**地写出来不要**漏字**也不要多**字** |

分成两个模型时，用户在预览里看到的和最终落进去的**不是同一句话**，而且是
**悄悄**不一样 —— 用户反馈「说 AI 识别不出」时，正是这个结构造成的：
落字（大模型）里有 AI、预览（小模型）里没有。

#### 为什么可以共用（速度实测）

| 音频时长 | 小模型 RTF | 大模型 RTF |
|---|---|---|
| 5.18s | 0.253（1311ms） | 0.256（1327ms） |
| 13.57s | 0.175（2373ms） | 0.189（2570ms） |

**流式识别两者几乎一样快**，所以共用只增加加载时间，不增加识别时的 CPU。

#### 代价：启动从 3 秒变成约 17–21 秒

大模型**同步加载要 16.8–22.8 秒**（解压后 2.0GB；`vosk_model_new` 要读 533MB 的
`HCLG.fst`、1.1GB 的 `G.carpa` 与 `rnnlm/final.raw`），而 `DESIGN.md` §6 的冷启动
预算是 3 秒。这是刻意的取舍：**预览在录音一开始就要用**，没法像以前那样
「后台慢慢加载、等精化时才用」；与其让用户在前 21 秒拿到一份和最终结果不一样的
预览，不如明确等一次。

于是必须有 `ui.LoadingWindow`：21 秒里没有任何反馈，用户会以为程序卡死了 ——
**等待本身不可怕，不知道为什么在等才可怕**。实测该窗口在启动 5 秒时可见、
加载完成后自动消失。

> 历史记录：这条路径曾用过 `engine.LazyVoskModel`（后台异步加载 + `Supplier` 惰性解析），
> 那是「预览用小模型」时代的方案。预览改用大模型后它已无意义并被删除 ——
> 异步加载的前提是「用模型的人可以等」，而预览的使用者**不能等**。

常驻内存约 **2.4GB**（`DESIGN.md` §6 的「空闲内存 < 500MB」这条预算在装了大模型时
不再成立——这是准确率换来的，必须如实记录）。

### 大模型的获取（已实测可行的路径）

`vosk-model-cn-0.22` 是 **1.3GB**，实测两条线路的差距是**700 倍**：

| 线路 | 实测速度 | 结论 |
|---|---|---|
| `alphacephei.com` 官方 | **18–48 KB/s** | 1.3GB 要 **约 19 小时**，不可用 |
| `hf-mirror.com/LiangJingyi/vosk-model-cn-0.22`（`model-cn.zip`） | **13 MB/s** | 1.3GB **89 秒**下完 |

```powershell
$dir = "$env:LOCALAPPDATA\TalkingLive\models"
$zip = Join-Path $dir 'model-cn.zip'
Invoke-WebRequest -UseBasicParsing -Uri `
  'https://hf-mirror.com/LiangJingyi/vosk-model-cn-0.22/resolve/main/model-cn.zip' -OutFile $zip
Expand-Archive -Path $zip -DestinationPath $dir -Force   # 解出 model-cn/，程序会自动识别
```

（注意：`localstack/vosk-models` 那个镜像仓**没有**大模型，只有 small 系列；
要找的是上面的 `LiangJingyi/vosk-model-cn-0.22`。）

### 结论（本节的判断）

- 代码层面**已无已知的准确率缺陷**：文本处理三版演进后已正确，注入链路已验证
  （逐字符码点核对通过），预览链路诊断已就位。
- 剩下的准确率差距**来自模型本身**，已通过「装好大模型即自动生效」解决；
  实测 `EngineBench` 于大模型：加载 17–21s、RTF 0.25–0.48、词级查询 0.008ms/词。
- 大模型**不支持运行时语法**（实测 C 侧输出
  `WARNING: Runtime graphs are not supported by this model`），
  所以唤醒/结束词检测仍走小模型——这个例外不是折中，是**唯一可行的结构**；
  除此之外**预览、落字、精化已经统一到同一个模型**，不再有「看到的和得到的不一样」。

## 7. 顺带确认的两条工程事实（原文档列为「未验证」）

### 7.1 词表查询的确切语义（附录 C 的落地依据）

`vosk_model_find_word` 的 C 签名是 **`int vosk_model_find_word(VoskModel*, const char*)`**，
返回**词 id**，**不在词表内返回 -1**。实测结果与 `DESIGN.md` 附录 B.1 的记录**逐条吻合**：

| 词 | 实测 wordId | 附录 B.1 记录 |
|---|---|---|
| 子曰 | **98204** | 98204 ✅ |
| 小助手 | 29194 | 29194 ✅ |
| 到此为止 | **87877** | 87877 ✅ |
| 结束 | 58069 | 58069 ✅ |
| 完毕 | 27351 | 27351 ✅ |
| 输入 | 11732 | 11732 ✅ |
| 本段结束 | **-1**（不在表内） | ❌ 不在表内 ✅ |
| 小秘书 / 好了 / 结束输入 | -1 | ❌ 不在表内 ✅ |

这条同时说明一件事：**把该函数声明成返回指针会得到完全错误的结果**——
id 数值会被当成地址，于是「任何词都像在词表内」，附录 C 的静默失效完全拦不住。
本仓库用 JNA 自己声明，并有一条冒烟自检专门守这个（`EngineSmoke`）。

### 7.2 受限语法的确切格式（踩过两次坑）

`vosk_recognizer_new_grm` 接受的是**纯 JSON 字符串数组**：

```json
["子曰","到此为止","[unk]"]
```

**不是** `{"phrase_list":[...]}`。后者是 Vosk **Python 绑定**的包装，它自己会把列表拆出来
再交给 C API（见 `kaldi_recognizer.cc`：`json::JSON::Load(grammar)` 之后直接 `obj.length()` / `obj[i]`）。
传对象进去的实测症状：

```
WARNING (VoskAPI:UpdateGrammarFst():recognizer.cc:283)
  Expecting array of strings, got: '{"phrase_list":["子曰","到此为止","[unk]"]}'
java.lang.Error: Invalid memory access
    at org.vosk.LibVosk.vosk_recognizer_new_grm(Native Method)
```

另外，**官方 Java 绑定不能用于中文**：它用 JNA 默认的**平台编码**加载原生库，
中文 Windows 上是 GBK，于是中文语法被编成 GBK 字节交给按 UTF-8 解释的 Vosk，
报的是同一行 `Expecting array of strings, got: '{"phrase_list":["??","????","[unk]"]}'`。
解决办法是自己声明 JNA 接口并在加载时指定 `OPTION_STRING_ENCODING=UTF-8`
（见 `system/VoskNative` 与 `system/VoskNativeLoader`）。

### 7.3 「大模型不支持运行时词表」有了代码级判据

`DESIGN.md` 附录 B.2 的结论（只有小模型支持运行时改词表）在 C 侧对应的判据是：
**模型是否同时加载了 `graph/HCLr.fst` 与 `graph/Gr.fst`**。
只有二者都存在时，`KaldiRecognizer(model, rate, grammar)` 才会真的用语法重建解码图；
否则它只打一行 `Runtime graphs are not supported by this model` 然后**忽略语法继续跑完整词表**——
唤醒词检测会悄悄失效。本仓库把这个判据实现成了
`VoskModel.supportsRuntimeGrammar()`，并在构造唤醒检测器时**硬校验**。

### 7.4 「英文唤醒词」为什么做不到（实测，别再试）

用户提过「唤醒词无法为英文」。查下来这不是代码缺陷，而是**中文 ASR 词表 + 受限语法**
这两个约束共同封死的结果。三条路都实测过：

**① 小模型没有英文词表。** 用 `vosk_model_find_word` 实测 48 个候选，
`hello` / `hi` / `ok` / `yes` / `computer` / `jarvis` / `siri` / `google`，
以及单字母 `A`–`Z`，**全部返回 -1**。能用的只有中文音译类词：
`小助手`(29194) / `你好`(2098) / `开始`(52701) / `小爱`(29243) / `小度`(29507) / `天猫`(6837)。

**② 换中英混合模型会丢掉运行时语法。** 实测 `vosk-model-cn-kaldi-multicn-0.15`（1.6GB）：
- 英文词表：`HELLO`(368) / `OK`(610) / `APP`(47) / `PC`(640) / `TV`(827) / `WIFI`(901) / `A`(3) / `I`(399) 在表内，
  但 `hello` / `jarvis` / `siri` 等仍不在；
- **`supportsRuntimeGrammar() == false`**（`graph/` 下只有 `HCLG.fst`，没有 `HCLr.fst`/`Gr.fst`）。

而唤醒词必须能自定义 → 必须支持运行时语法。**两个条件互斥**：
有语法的模型（small）没有英文；有英文的模型（multicn / 大模型）没有语法。

**③ 最反直觉的一条：中文 ASR 会把英文词听成汉字音译。**
用英文嗓音念 "hello"，走**自由识别**（不受语法限制）：

| 模型 | 识别结果 |
|---|---|
| `vosk-model-small-cn-0.22` | `好` |
| `vosk-model-cn-kaldi-multicn-0.15`（中英混合） | **`哈喽`** |

即使换中英混合模型，也说不出 "hello" —— 它输出的是中文音译 `哈喽`。
所以「检测到英文单词 hello」这个思路本身就不成立。

**结论（当时的）**：唤醒词只能是**中文词**，且必须在唤醒模型词表内。
代码现在会在设置窗口硬校验并给出可用的备选（`WordSuggestions`），这是当前唯一正确的处理。
`vosk-model-cn-kaldi-multicn-0.15` 实测后已删除（2.6GB 换不来能力，且它的目录名会干扰
大模型自动探测）。

**如果将来一定要拼音/英文唤醒**，唯一可行的方向是**自训**：
用 Kaldi 给该词生成发音词典、重新编译 HCLG，再用语料训练。这远超本项目范围，
且失去「装个模型就能用」的部署特性。建议不做。

> ⚠️ **这个「建议不做」的结论后来被推翻了 —— 见 §7.5。上面三条实测都成立，
> 但由它们推出的最后一步是错的。**

---

### 7.5 英文唤醒词其实**可以**做：分词的粒度是「词表条目」，不是「词」

用户没有接受 §7.4 的结论，追问「唤醒词无法为英文」。重查之后发现 §7.4 漏了一个关键点：

**§7.4 全程在验证「某个*词*在不在词表内」，但受限语法接受的是一串 *token*，
而 token 的粒度是词表条目 —— 单字也是词表条目。**

于是「整词不在词表内」和「每个字不在词表内」完全是两件事。
`Firay` 的汉字写法「飞瑞」：整词不在表内（实测两字组合 `fēi` × `ray` 共 100 种，
**0 命中**），但 `飞`(73020) 与 `瑞`(80694) 各自都在表内。把语法写成
**两个单字 token** 就能匹配：

| 语法 | 说「飞瑞」识别为 | 说「非为」 | 说「飞雷」 | 说「小助手」 |
|---|---|---|---|---|
| `["飞瑞","[unk]"]`（整词，不在词表） | `[unk]` | `[unk]` | `[unk]` | — |
| `["飞","瑞","[unk]"]`（单字序列） | **`飞瑞`** ✅ | `非为` | `飞` | `[unk]` |
| `["非","为","[unk]"]` | `非为` | **`非为`** ✅ | `非为` | `[unk]` |
| `["小助手","[unk]"]`（整词对照） | `[unk]` | `[unk]` | `[unk]` | **`小助手`** ✅ |

（音频：Windows TTS 中文嗓音；识别：`vosk-model-small-cn-0.22` 受限语法。
复现脚本 `target/p7/GrammarSeqProbe.java`，结论已固化进
`src/test/java/com/talkinglive/engine/WakePhraseTest.java` 与自检。）

**所以「英语唤醒词」= 把英语发音写成汉字，一个字一个字地写。**
中文模型依然发不出 `Firay`（词表内拉丁 token 实测为 0 个），但它能稳稳地听出「飞瑞」——
用户得到的正是自己想要的发音，只是输入时写成汉字。

**代价（必须让用户知道）**：单字在正常说话里出现得太频繁，所以拆字后的误触发率
高于整词。据此定了三条实现约束：

1. **只在整词不在词表内时才拆**（`WakePhrase.resolve` 先查整词），绝不主动拆一个
   词表里有的词；
2. **命中判定用整体相等**，不是包含 —— 只说「飞」或只说「瑞」都不算命中；
3. **拆了几段、每段是哪个字必须写进日志并显示在设置窗口**，否则用户"说了没反应"
   时无从排查。

**适用边界**：只有**唤醒词**能拆。结束词**不拆** —— 结束词命中的后果是"立刻停止录音"，
而单字太容易误触发；整词严格匹配，宁可让用户换个说法。

**顺带修正 §7.4 的第 ③ 条**：那条说「中文 ASR 把英文听成汉字音译，所以检测英文单词
的思路不成立」—— 现在看，那恰恰是**这条路的证据**，而不是它的反例。
问题只在"我们只试了整词，没试过让它逐字输出"。

> ⚠️ **但 §7.5 也不是"英文唤醒词"的完整答案 —— 见 §7.6。**
> 它解决的是"用汉字拼出英语发音"，不是"让模型认出英文单词"。

---

### 7.6 真正的英文唤醒词：能用的只有**词表内的英文词**（实测三组）

用户要的是"英文唤醒词"，§7.5 的汉字拼法只是近似。查下来 Vosk 官方英文小模型
`vosk-model-small-en-us-0.15`（**39.3 MB**）是唯一可能的方向，实测三组：

**① 它支持运行时语法 —— 前提成立。** 下载解压后 `graph/` 下有
`HCLr.fst`(21.4MB) + `Gr.fst`(22.9MB)，`supportsRuntimeGrammar() == true`。
这正是 `vosk-model-cn-kaldi-multicn-0.15` 缺的东西（那个模型有英文词表但没语法，
所以早就被淘汰）。

**② 语法**能**为词表外的词构建 —— 但认不出来。** 这是本次最容易误判的一点：

```
语法 ["firay","[unk]"]    构建成功（English 模型按**音素**建语法，不像中文模型直接忽略表外词）
                          LOG: Created language model with 2 states and 2 arcs
说「Firay」→ 「[unk]」      ← 不命中
自由识别   → 「theory」     ← 它只能把这串音听成别的词
```

原因：语法图是按发音词典建的，`firay` 在**发音词典里没有条目**，所以没有任何音素序列
能到达那个词。**"语法构建成功"不等于"能识别"** —— 只看日志会得出相反的结论。

**③ 词表内的英文词完全可用。** 同一次实验里的对照：

| 说的词 | 语法 | 结果 |
|---|---|---|
| computer / jarvis / alexa / siri | 各自单词 | **全部命中 ✓** |
| "Hey Google" | `["hey google","[unk]"]` | **命中 ✓**（两词短语可行） |
| **firay** | `["firay","[unk]"]` | **`[unk]` ✗**（词表外，预期失败） |
| 无关音频「Firay」 | `["computer","stop listening","[unk]"]` | `[unk]` ✓（不误命中） |

结束词同样能走英文：`["computer","stop listening","[unk]"]` 一个语法里，
说 computer 命中唤醒、说 stop listening 命中结束，互不干扰。

**结论（可用于产品决策）**：

- **"Firay" 这类自造英文词，两条路都走不通**：中文模型没有拉丁词表；英文模型的
  发音词典里也没有它。想让它能用只有**自训**（造发音词典、重编 HCLG、训语料），
  远超本项目范围。
- **想要英文唤醒词，唯一现实做法是选一个在英文词表内的词** ——
  `computer` / `jarvis` / `alexa` / `siri` / `hey google` 等实测可用。
- 代价：唤醒检测要**额外加载一个 39MB 的英文模型**（中文听写仍用原模型，
  唤醒模型与听写模型本来就是分开的，所以只是多一份常驻内存）。
- 如果用户只想要"听起来像 Firay"，则 §7.5 的汉字拼法（「飞瑞」）是**已实测可用**的近似，
  不需要第二个模型 —— 但它不是英文识别，真人语音上的稳定性尚未验证。

**记录一条方法论教训**：这一节推翻了自己两次。第一次（§7.5）是"只验证了整词，
没验证分词粒度"；第二次是"只看语法构建成功的日志，没喂音频验证能不能认"。
**两次都是把"机制上可行"当成了"实测可用"。** 引擎能力必须以**音频结果**为准。

## 8. ITN 取舍（`TECH-PLAN` §8 #2）

- **当前精化路径（Vosk 离线重跑）没有 ITN**，因此不存在「改字」风险。
- 历史上有一个 `AppConfig.itn` 字段（默认 `true`），它只被存/读/写/打日志，
  **没有任何地方读它来做事** —— 因为它在等从未接入的 SenseVoice。
  一个"改了没反应"的开关比没有这个功能更糟（用户会以为软件坏了），
  所以 0.9.0 的清理中**已删除**。SenseVoice 接入后再按 §6.3 的方法测
  「数字与英文是否被规整成错误内容」，然后决定要不要加回这个开关。
