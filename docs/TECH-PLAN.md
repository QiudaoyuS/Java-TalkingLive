## 1. 结论与本方案要裁决的事

### 1.1 已定的部分（本文直接沿用，不再讨论）

| 项 | 选择 | 定因 |
|---|---|---|
| 语言与运行时 | **JDK 21** | 开发者熟悉；JDK 已装（`D:\Code\Java\jdk-21.0.12.1`） |
| 构建 | **Maven Wrapper**（`mvnw`） | 只需 JDK，不额外安装 |
| UI 工具包 | **Swing / AWT** | `JWindow` 直接暴露 HWND，配 JNA 设 `WS_EX_NOACTIVATE` 最自然；已由原型验证 |
| Win32 互操作 | **JNA** | 注入、前台窗口监听、扩展样式、光标定位 |
| 交付形态 | **单机 Windows 桌面、单进程、全离线** | 产品定位（`DESIGN.md` §1.4） |
| 打包 | **jpackage** | JDK 自带，产出带运行时的 exe |
| 测试 | **JUnit 5**；核心逻辑不得依赖 AWT/JNA/引擎原生库 | `DESIGN.md` §4.5 / §9.1 |

这些不再有争议，**M0 可以直接开工**。

### 1.2 本文要裁决的事

**识别引擎组合**（以及由它派生出来的「要不要依赖核显」「模型选多大」「§6 延迟指标怎么定」）。

原因见 §4：`DESIGN.md` 当前的双引擎方案（`DESIGN.md` §4.2）建立在 Step 0 的结论上，
而 Step 0 只验证了「词在不在词表里」和「谁支持运行时动态词表」，
**没有测纯 CPU 推理速度**。补上这个维度后，结论会变。

### 1.3 一句话摘要

> 按实测数据推算，**whisper-small 在目标机器纯 CPU 上处理 5 秒音频需约 12–15 秒**
> （§4.2），与 `DESIGN.md` §6 的「提交延迟 < 2.5s」相差一个数量级。
> 因此「选择哪个识别引擎」不是性能调优问题，而是**架构可行性问题**，
> 且它直接决定本产品**能否不依赖核显**。故先做一次约半天的纯 CPU 引擎实测（§6）
> 再定架构，而不是先开工。

## 2. 先明确：本产品的硬约束

技术选型的自由度比看上去小得多。下面每条都是**排除性**的——不满足就直接出局。

| # | 约束 | 来源 | 排除了什么 |
|---|---|---|---|
| 1 | 必须能低成本调用 Win32（`SendInput` / 窗口样式 / 光标定位 / 前台窗口钩子） | 注入到任意应用、悬浮球不抢焦点 | 纯 WebView 外壳；纯跨平台抽象层 |
| 2 | 必须能拿到原生 HWND 并设置扩展样式 | `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW` | 封装了 HWND 的 UI 框架 |
| 3 | 全部离线、单进程、不联网 | `DESIGN.md` §1.3 / §4.1 | 全部云端听写服务；依赖网络下载模型的启动路径 |
| 4 | 常驻后台、空闲内存 < 500MB、空闲 CPU < 2% | `DESIGN.md` §6 | 内嵌 Chromium（Electron）；把大模型常驻内存 |
| 5 | 「说完一段 → 文字出现在光标处」要在秒级完成 | `DESIGN.md` §2.2 第 5 步 / §6 | 慢速推理引擎；**见 §4，这条是当前最大的风险** |
| 6 | **零环境依赖**：不得要求用户具备特定硬件能力 | 自用工具；见 §3 | 把核显/Vulkan 作为必需品 |

第 4 条要额外说明：内存预算卡住的不只是 UI 框架，**也卡住了模型体积**。
`DESIGN.md` §6 写的「听写中内存 < 1.5GB」需要把「常驻模型」和「段落 PCM 缓存」
一起算进去，这条会在选定引擎后重新回填。

## 3. 核心决策：GPU 只能是可选项，不能是必需品

这是本文最重要的一条，它决定了后面所有候选方案的取舍标准。

### 3.1 决策

**把「纯 CPU 完整可用」定为设计红线。** 即：产品在没有任何 GPU 加速能力的机器上，
必须完整可用；核显/CUDA 只能作为**可选的、默认关闭的**加速项。

### 3.2 理由

不是出于「照顾弱机器」的泛泛兼容性，而是三条具体的：

1. **失败时用户就是开发者本人。** 自用工具同样会遇到：系统重装、换机器、
   临时借用别人的电脑、驱动被 Windows Update 换掉。而 Intel 核显的 Vulkan 能力
   对驱动版本敏感，这个失败面是真实存在的。**出问题的那一刻，正是想用打字的时候。**
2. **会让「性能」变成「环境依赖」。** 一旦 GPU 成为必需品，
   `DESIGN.md` §6 的预算表、§9.3 的验证清单、§11 的 go/no-go 判断，
   全部要按「用户的驱动恰好正常」来写。这种不确定性对个人项目是最贵的成本。
3. **上游后端自身仍在反复。** whisper.cpp 的 Vulkan 后端出现过
   [同类问题](https://github.com/ggml-org/whisper.cpp/issues/3455)。
   把产品地基压在一个还在迭代的后端上，风险与收益不对等。

### 3.3 一个澄清：Vulkan 本身不是坏技术

需要区分「Vulkan 的性能」和「Vulkan 的依赖」两件事：

- 性能上，实测 Vulkan 与 CUDA 在同卡上**只差约 1%**
  （11 秒音频、small 模型：CUDA 0.84s / Vulkan 0.82s），
  所以它不是「为了跨厂商而牺牲性能」。
- 问题**纯粹在于它多引入了一个可以失败的前提**。

因此本文不反对将来支持 GPU，反对的是**把它变成必需**。

## 4. 关键发现：现有架构在纯 CPU 上的可行性

### 4.1 问题的来源

`DESIGN.md` §4.2 的双引擎分工（小 Vosk 做唤醒/预览 + whisper 做转写精化）
由 Step 0 的数据推导而来（`DESIGN.md` 附录 B.2）：Vosk 小模型 CER 17% 不足以直接转写，
而 whisper 准确率更高且原生带标点。**这个推导没有问题，但它只在「准确率」这个维度上做过比较。**

Step 0 **没有测的维度**是：whisper 在纯 CPU 上到底多慢。

### 4.2 实测数据与推算

**【实测·外部】whisper.cpp 官方 `jfk.wav`（11 秒音频），Windows，8 线程，best of 2：**

| 模型 | 纯 CPU 耗时 | 实时倍率 | CUDA | Vulkan |
|---|---|---|---|---|
| tiny | 1.98s | 5.6x | 0.32s | 0.31s |
| base | 4.54s | 2.4x | 0.41s | 0.42s |
| **small** | **20.4s** | **0.5x** | 0.84s | 0.82s |
| medium | 73.6s | 0.1x | 1.91s | 2.02s |
| large-v3 | 133.5s | 0.1x | 3.90s | 3.73s |

> 测试机为 i9-13980HX + RTX 4090 Laptop。
> 来源：[StarWhisper Windows 基准](https://starwhisper.ai/whisper-benchmark.html)（CC BY 4.0）。

**【推算】折算到本产品目标机器 i7-12650H（6P+4E，弱于上表 i9 约 25–35%），
一段 5 秒语音的纯 CPU 精化耗时：**

| 模型 | 推算耗时 | 对「提交延迟 < 2.5s」 |
|---|---|---|
| tiny | ~1.5s | ✅ 但模型太小，中文质量存疑 |
| base | ~2.5–3s | ⚠️ 贴线，且质量未必够 |
| **small** | **~12–15s** | ❌ **差一个数量级** |
| medium 及以上 | 40s+ | ❌ 不可用 |

### 4.3 结论

> **纯 CPU + whisper-small 达到 §6 的提交延迟目标，不是「紧」，是数学上不可能。**

而 small 已经是 whisper 里「中文质量勉强能用」的下限档（base/tiny 更小）。
换句话说：**「坚持 whisper 精化」与「不依赖核显」两者，当前架构下不可兼得。**

这正是 §3 那条红线暴露出来的第一个具体冲突。

## 5. 候选方案

四条候选，**唯一区别在引擎组合**，其余技术栈（§1.1）完全相同。

| 方案 | 唤醒/结束词 | 实时预览 | 段落精化 | 引擎数 | 纯 CPU 可行 | 数据源 |
|---|---|---|---|---|---|---|
| **A 现状** | 小 Vosk（受限语法） | 小 Vosk 流式 | **whisper.cpp** | 2 | ❌（§4） | Step 0 已验 |
| **B 单引擎** | 待定（KWS 或流式模型） | SenseVoice + VAD 分段 | 同一个 SenseVoice | **1** | ✅ | sherpa-onnx |
| **C 折中** | 小 Vosk（不变） | 小 Vosk 流式（不变） | **SenseVoice** | 2 | ✅ | sherpa-onnx |
| **D 流式替代** | 流式模型自身 | 流式 Zipformer/Transducer | 同一流式模型 | **1** | ✅ | sherpa-onnx |

### 5.1 方案 A（现状）——判定为不可行

| | |
|---|---|
| **优点** | Step 0 已实测；`DESIGN.md` 全套设计围绕它写；whisper 中文质量与原生标点已知可用 |
| **致命项** | 纯 CPU 精化需 12–15s，**必须有核显**，直接违反 §3 红线 |
| **其它** | 两套引擎、两套原生库、两套绑定、两套加载/线程管理；§8「预览与最终文本不一致」风险存在 |

**结论：不采用，除非实验证明 §5.2 的三条路线全部不达标。**

### 5.2 方案 B（单引擎 SenseVoice + VAD 分段）

| | |
|---|---|
| **做法** | Silero VAD 切语音段 → 每段交给 SenseVoice → 文本追加进浮窗；段落结束用同一引擎处理整段 |
| **优点** | ① **纯 CPU 实时倍率约 0.1**（实测：12.744s 音频 / 1.392s ≈ 0.109，见附录 A），5 秒音频约 0.5s；<br>② 原生带标点（`use_itn=1`）；<br>③ **一个引擎**，省掉一整套原生库与绑定；<br>④ 预览与最终是同一份文本，`DESIGN.md` §8「预览与最终不一致」风险**直接消失**；<br>⑤ 引擎改主意（demo 里 `这个需球 → 这个需求`）现象消失 |
| **代价** | **预览不再是逐字生长，而是按语音段整句追加**。首字延迟由「数百 ms」变为「等第一个语音段结束，约 1–3s」；浮窗的「两级文字样式」（稳定 / 仍在变）失去意义 |
| **未决** | 唤醒词/结束词的承载方式待定（SenseVoice 不支持运行时动态词表，需配 KWS 模块或另定方案） |
| **性质** | 这是**产品体验层的取舍**，不是技术问题。见 §8 待决问题 #1 |

### 5.3 方案 C（折中：Vosk 预览 + SenseVoice 精化）

| | |
|---|---|
| **做法** | 预览侧完全不动（小 Vosk 流式），只把**段落精化**从 whisper.cpp 换成 SenseVoice |
| **优点** | ① **预览体验零损失**——这是产品最难做、也最不该动的部分；<br>② 精化从 12–15s 降到约 0.5s，纯 CPU 达标；<br>③ 标点由引擎原生输出，比自研 `PunctuationProcessor` 可靠；<br>④ 只需维护 Vosk 一家原生库，**砍掉整条 whisper.cpp 集成链**（这是全链上最重的一块：JNI 绑定、模型格式、后端编译） |
| **代价** | 仍是两个引擎（但第二个极轻）；`DESIGN.md` §3.4 里 `PunctuationProcessor` 的职责需要下调（见 §9） |
| **性质** | **风险最低的方案**：把最大的不确定性（预览）保持原样，只替换链条末端那一步 |

### 5.4 方案 D（流式替代：sherpa-onnx 流式模型）

| | |
|---|---|
| **做法** | 用一个中文流式模型（如流式 Zipformer / Transducer）同时承担预览与最终输出，靠**热词**机制解决唤醒词与自定义词 |
| **优点** | 若成立则最优：**一个引擎、流式、原生标点、原生热词**，且纯 CPU 可行；`TextRefiner` 接口可彻底退化为「留给未来云端引擎」 |
| **代价/风险** | 三个前提全部**未验证**：① 中文流式准确率是否够用；② 热词（contextual biasing）中文效果如何；③ 纯 CPU 实时倍率是否达标 |
| **性质** | 收益最高、不确定性也最高。**必须先做 §6 的验证** |

### 5.5 关于「精化」这一步的再思考

先摆一条事实，它会影响 B/C/D 的选择：

> 精化之所以存在，是因为**预览引擎（Vosk 小模型，CER 17%）不够准**，
> 所以段末要用一个更准的引擎重跑一遍。

如果最终引擎在 CPU 上已经快到这个程度：

| 引擎 | 5 秒音频耗时（推算） |
|---|---|
| whisper-small | ~12–15s |
| SenseVoice | ~0.5s |

那么「用糙的做预览、用准的做精化」这套分工就**失去了一半理由**——
`TextRefiner` 从「段末必须做一次慢推理」变成「一次代价很小的复核」。

**但 B/C/D 的选择不完全由它决定**，因为还差一个变量：**预览引擎的准确率**。
若某流式模型准确率已足够，方案 D 最优（连预览都不用换两套）；
若流式准确率仍不够，则 C 是稳妥解；
若愿意用预览体验换掉一整个引擎，则 B 是简化解。

—— 这三个分支，正是 §6 实验要一次性回答的。

## 6. 先导验证实验（Lead Experiment）

**目的**：在纯 CPU 上一次性回答 §5 未决的三个变量
（**准确率**、**延迟**、**流式与热词能力**），据此在 A/B/C/D 之间裁决。

**成本**：约半天。**不写 Java 代码**——sherpa-onnx 与 whisper.cpp 均提供 Windows 预编译二进制，
本实验全程在命令行完成。

### 6.1 原则

1. **以真实使用场景为准**：测试音频必须是**自己录的中文口语**，
   内容要包含**本工作领域的专业术语**（这才是热词/纠错要解决的问题，
   也是各家模型拉开差距的地方）。
2. **同一段音频跑遍所有引擎**，避免用不同音频比较。
3. **所有数字记原始值**，不记「感觉快了」，便于事后复算与回填 `DESIGN.md` §6。

### 6.2 步骤 1：准备测试集

- 录 **6–8 段**中文语音，每段 **5–15 秒**。
- 内容覆盖三类：① 日常口述；② 含专业术语（从 `DESIGN.md` 或代码注释里挑句子念）；③ 含数字与英文混说。
- 每段配一份**人工参考文本**（用来算 CER / 比对差异）。
- 保存为 **16kHz / 16bit / 单声道 wav**——这是所有候选引擎的共同输入格式，
  也顺带验证了 `DESIGN.md` §10.3 的模型放置约定是否顺手。

### 6.3 步骤 2：准备引擎与模型

| 引擎 | 用途 | 获取方式 |
|---|---|---|
| sherpa-onnx（Windows 预编译） | 跑 SenseVoice 与流式模型 | 官方 releases 页面的 Windows 包 |
| `sense-voice-zh-en-ja-ko-yue-int8` | 方案 B / C 的精化引擎 | sherpa-onnx 官方模型页 |
| Silero VAD（`silero_vad.onnx`） | 方案 B 的分段 | 同上 |
| 一个中文**流式**模型 | 方案 D | 同上（流式 transducer / zipformer 系列） |
| whisper.cpp（Windows 预编译） | 方案 A 的基线 | 官方 releases 页面 |
| whisper `base` + `small` | 纯 CPU 基线参照 | 同附录 A |

> 「小 Vosk」不需要另测：Step 0 已验（`DESIGN.md` 附录 B），
> 本实验只需把它作为**预览侧的前提**保留。

### 6.4 步骤 3：执行与记录

对每段音频、每个配置，记录：

| 指标 | 说明 |
|---|---|
| **纯 CPU 耗时（秒）** | 单段推理的墙钟时间 |
| **RTF** | 耗时 / 音频时长；< 1 才可能用于实时场景 |
| **输出文本** | 原文照抄，用于人工比对 |
| **CER** | 与参考文本比对（可用一次性脚本算，不进仓库） |
| **标点质量** | 有无标点 / 是否正确成句 |
| **数字与英文** | 是否被规整、是否被改错（注意 ITN 会**改字**，不只是加标点） |
| **术语正确率** | 专业术语是否写对——**这是热词机制价值的直接体现** |
| **（流式模型）首字延迟** | 开始说话到第一个字出现 |
| **（流式模型）热词是否生效** | 加入自定义词后，术语正确率是否提升 |

**特别提醒**：`num_threads` 会影响结果，且它和 `DESIGN.md` §6 的
「空闲 CPU < 2%」直接冲突（推理时会把线程跑满）。实验时同时记录
**1 线程 / 4 线程 / 默认**三档，为后面定「转写中 CPU 预算」提供依据。

### 6.6 判读规则（事先定好，避免事后找理由）

按顺序判断，**前一条成立就不看后面的**：

| # | 条件 | 裁决 |
|---|---|---|
| 1 | 流式模型：**CER 达标** 且 **热词生效** 且 **纯 CPU RTF < 1** | → **方案 D**（最优） |
| 2 | SenseVoice：**CER 达标** 且 **纯 CPU 5 秒音频 < 1s** | → **方案 C**（保留流式预览）；若同时接受「整句蹦出」的预览体验，则 **方案 B**（更简） |
| 3 | 只有 whisper-small 达标 | → **回到 §3 红线做取舍**：接受核显依赖，或在「更小的模型 + 更慢的提交」之间选一个 |
| 4 | 全部不达标 | → 重新评估产品定位：缩范围（如只做短句）、或接受「说完等几秒」的交互 |

**判定「达标」的具体阈值，在实验开始前由本人确认并写死**（避免结果出来后再调标准）。

## 7. 与此并行的工程项（不依赖实验结论，M0 可同时做）

以下各项**与引擎选型无关**，无论 A/B/C/D 哪个胜出都要做，因此不必等实验：

| # | 项 | 说明 |
|---|---|---|
| 1 | **修正 `JAVA_HOME`** | 实测当前 `JAVA_HOME=D:\Code\Java\jdk1.8.0_111`，而 PATH 里的 `java` 是 21.0.12.1。Maven Wrapper 优先读 `JAVA_HOME`，**M0 开工即会踩**。`DESIGN.md` §10.1 已预警但未修 |
| 2 | **音频重采样** | `DESIGN.md` §3.1/§4.1 只写「16kHz」，但真实麦克风设备原生格式通常是 48kHz，且 `TargetDataLine` 不保证按请求格式打开。**这是当前设计里最大的空白**，写错的症状是「识别不准」——最难查。需在采集层显式处理并单测 |
| 3 | **文本注入的降级路径** | `DESIGN.md` §7 只覆盖了「目标以管理员运行」一种失败面。实际还有 Electron/Chromium、DirectInput 游戏、自绘输入框等。建议保留 `SendInput` 为主路径，增加**剪贴板 + Ctrl+V（带剪贴板恢复）**作为可配置降级，并在 §9.3 手工清单里覆盖 4 类目标应用 |
| 4 | **DPI 感知模式** | `DESIGN.md` §4.4 的「Win32 物理像素 vs Java 逻辑像素」判断正确，但根因没说透：AWT 的坐标空间取决于**进程的 DPI awareness 设置**。结论：进程级统一 awareness，并把**所有跨边界换算收敛到单一工具类**，禁止任何地方混用 `Robot.mouseMove` 与 `SetCursorPos` |
| 5 | **UI 观感** | 引入 **FlatLaf**（单一依赖）改善设置窗口外观。悬浮球/浮窗是自绘，不受影响 |
| 6 | **日志** | 用 **SLF4J + Logback** 实现 `DESIGN.md` §3.1 第 12 项的「滚动 5MB×3、不记转写内容」，比手写 `FileHandler` 稳 |
| 7 | **补给 §6 的 CPU 预算** | `DESIGN.md` §6 只定了「空闲 CPU < 2%」，**没有定「转写中的 CPU 占用」**。推理必然短时占满多核，需补一行目标值（建议限制线程数并给峰值上限），依据来自 §6.4 的实验记录 |

## 附录 A：本方案引用的数据来源与口径

**原则：每条数据标注「实测」或「推算」，并给出测试条件，便于事后复算。**

### A.1 whisper.cpp 各模型速度（实测·外部）

- 条件：Windows，`whisper-cli`，8 线程，输入为标准 11.0 秒 `jfk.wav`，每配置取两次最优
- 硬件：Intel Core i9-13980HX + RTX 4090 Laptop，32GB RAM，Windows 11
- 口径：耗时含推理，排除一次性的模型加载；RTF = 音频时长 / 处理耗时
- 来源：[StarWhisper Windows 基准](https://starwhisper.ai/whisper-benchmark.html)（CC BY 4.0）
- **注意**：该文自述「是速度测量，不是准确率排名」

### A.2 SenseVoice 速度（实测·外部）

- 条件：`sherpa-onnx-offline`，`--num-threads=1`，int8 量化模型
- 实测样例：12.744 秒音频 → 1.392～1.396 秒，**RTF ≈ 0.109～0.110**；
  含 ITN（`--sense-voice-use-itn=1`）时耗时基本相同
- 来源：[sherpa-onnx SenseVoice 预训练模型页](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)
- **口径校正**：上表为 **Mac** 实测；同页另有 **RK3588 嵌入式 CPU** 数据
  （Cortex-A76 单线程 0.099 / 双线程 0.065 / 三线程 0.049；
  Cortex-A55 单线程 0.436）。**x86 桌面 CPU 会明显更快，但需本地复测确认**
- 标点能力：官方写明设 `use_itn=1` 输出标点；样例输出
  `"开放时间早上9点至下午5点。"`（含数字规整）

### A.3 GPU 与 CPU 的差距（实测·外部）

- Vulkan vs CUDA：同卡同模型**差距约 1%**（small：0.82s vs 0.84s）
- iGPU 的 Vulkan 收益：官方口径宣传「12x」，**但那是原始吞吐口径**；
  实测机为 Ryzen 7 6800H 与 Core Ultra 7 155H，
  **真实 RTF 提升为 3–4 倍**；CPU-only 基线 RTF ≈ 0.3
- 来源：[LavX 关于 whisper.cpp 1.8.3 的报道](https://news.lavx.hu/article/whisper-cpp-1-8-3-unlocks-12x-speedup-for-speech-recognition-on-integrated-amd-and-intel-gpus)
- **注意**：两处 iGPU 数据均**不是**本产品的目标机器，不可直接套用

### A.4 i7-12650H 折算（推算）

- 基准：A.1 的 i9-13980HX（第 13 代，更多核心与更高频率）
- 折算幅度：**-25% ~ -35%**（凭规格粗略估计，**必须实测替换**）
- 用途：仅用于说明数量级（本方案 §4.2 的结论是「差一个数量级」，
  在这个量级的差距面前，折算误差不影响结论）
