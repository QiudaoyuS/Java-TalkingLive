## 1. 结论

### 1.1 已定：架构采用方案 C

> **预览侧完全不动，只替换精化引擎。**
>
> | 职责 | 引擎 | 变化 |
> |---|---|---|
> | 唤醒词 / 结束词检测 | 小 Vosk（受限语法） | **不变**（沿用 `DESIGN.md` §3.1 第 5 项） |
> | 实时预览 | 小 Vosk（流式） | **不变**（沿用 `DESIGN.md` §3.1 第 6 项） |
> | 段落精化 | ~~whisper.cpp~~ → **SenseVoice**（sherpa-onnx） | **替换** |

**定这条的理由**：纯 CPU 不可行的**根源在精化引擎**（§4），不在预览引擎。
因此只需替换链条末端那一步——`DESIGN.md` §4.4 里"最难做、做错则产品直接废掉"的
浮窗预览条、逐字生长体验、两级文字样式（已稳定 / 仍在变），以及已被 demo 验证过的
那一整套交互，**全部保持原样，不承担任何风险**。

### 1.2 技术栈（已定，不再讨论）

| 项 | 选择 | 定因 |
|---|---|---|
| 语言与运行时 | **JDK 21** | 开发者熟悉；JDK 已装（`D:\Code\Java\jdk-21.0.12.1`） |
| 构建 | **Maven Wrapper**（`mvnw`） | 只需 JDK，不额外安装 |
| UI 工具包 | **Swing / AWT** | `JWindow` 直接暴露 HWND，配 JNA 设 `WS_EX_NOACTIVATE` 最自然；已由原型验证 |
| Win32 互操作 | **JNA** | 注入、前台窗口监听、扩展样式、光标定位 |
| 交付形态 | **单机 Windows 桌面、单进程、全离线** | 产品定位（`DESIGN.md` §1.4） |
| 打包 | **jpackage** | JDK 自带，产出带运行时的 exe |
| 测试 | **JUnit 5**；核心逻辑不得依赖 AWT/JNA/引擎原生库 | `DESIGN.md` §4.5 / §9.1 |
| 识别引擎 | **小 Vosk（唤醒+预览）+ SenseVoice（精化）** | 本文 §1.1 / §3 |

这些不再有争议，**M0 可以直接开工**。

### 1.3 仍需验证：精化引擎能否胜任

架构定了，但**方案 C 的可行性取决于一个未验证的前提**：

> SenseVoice 在"精化"这个角色上，能否达到或超过 whisper 的效果？

这需要一次约半天的验证（§6）。**它与架构决策无关**——架构已经定了，
这次验证是为了给 SenseVoice 的落地做准备，并回填 `DESIGN.md` 的数值指标。
若验证不通过，回退路径见 §6.6。

### 1.4 一句话摘要

> 按实测数据推算，**whisper-small 在目标机器纯 CPU 上处理 5 秒音频需约 12–15 秒**
> （§4.2），与 `DESIGN.md` §6 的「提交延迟 < 2.5s」相差一个数量级。
> 而 SenseVoice 是**非自回归**架构，纯 CPU 实时倍率约 0.1（5 秒音频约 0.5 秒），
> 且原生带标点。因此**用 SenseVoice 替换 whisper 做精化**，
> 在不动预览侧的前提下解决纯 CPU 可行性问题。

## 2. 先明确：本产品的硬约束

技术选型的自由度比看上去小得多。下面每条都是**排除性**的——不满足就直接出局。

| # | 约束 | 来源 | 排除了什么 |
|---|---|---|---|
| 1 | 必须能低成本调用 Win32（`SendInput` / 窗口样式 / 光标定位 / 前台窗口钩子） | 注入到任意应用、悬浮球不抢焦点 | 纯 WebView 外壳；纯跨平台抽象层 |
| 2 | 必须能拿到原生 HWND 并设置扩展样式 | `WS_EX_NOACTIVATE` / `WS_EX_TOOLWINDOW` | 封装了 HWND 的 UI 框架 |
| 3 | 全部离线、单进程、不联网 | `DESIGN.md` §1.3 / §4.1 | 全部云端听写服务；依赖网络下载模型的启动路径 |
| 4 | 常驻后台、空闲内存 < 500MB、空闲 CPU < 2% | `DESIGN.md` §6 | 内嵌 Chromium（Electron）；把大模型常驻内存 |
| 5 | 「说完一段 → 文字出现在光标处」要在秒级完成 | `DESIGN.md` §2.2 第 5 步 / §6 | 慢速推理引擎；**见 §4，这条是当前最大的风险** |
| 6 | **零环境依赖**：不得要求用户具备特定硬件能力 | 自用工具；见 §3.1 | 把核显/Vulkan 作为必需品 |

第 4 条要额外说明：内存预算卡住的不只是 UI 框架，**也卡住了模型体积**。
`DESIGN.md` §6 写的「听写中内存 < 1.5GB」需要把「常驻模型」和「段落 PCM 缓存」
一起算进去，这条会在选定模型后重新回填（§7 第 7 项）。

## 3. 核心决策：纯 CPU 必须完整可用

### 3.1 决策

**把「纯 CPU 完整可用」定为设计红线。** 即：产品在没有任何 GPU 加速能力的机器上，
必须完整可用；核显/CUDA 只能作为**可选的、默认关闭的**加速项。

方案 C 的选择正是为了在**不触碰红线**的前提下解决性能问题——
SenseVoice 在纯 CPU 上已足够快，核显依赖被直接消除，而不是被管理。

### 3.2 理由

不是出于「照顾弱机器」的泛泛兼容性，而是三条具体的：

1. **失败时用户就是开发者本人。** 自用工具同样会遇到：系统重装、换机器、
   临时借用别人的电脑、驱动被 Windows Update 换掉。而 Intel 核显的 Vulkan 能力
   对驱动版本敏感，这个失败面是真实存在的。**出问题的那一刻，正是想用打字的时候。**
2. **会让「性能」变成「环境依赖」。** 一旦 GPU 成为必需品，
   `DESIGN.md` §6 的预算表、§9.3 的验证清单、§11 的 go/no-go 判断，
   全部要按「用户的驱动恰好正常」来写。这种不确定性对个人项目是最贵的成本。
3. **上游后端自身仍在反复。** whisper.cpp 的 Vulkan 后端出现过
   [同类问题](https://github.com/ggml-org/whisper.cpp/issues/3455)。
   把产品地基压在一个还在迭代的后端上，风险与收益不对等。

### 3.3 一个澄清：Vulkan 本身不是坏技术

需要区分「Vulkan 的性能」和「Vulkan 的依赖」两件事：

- 性能上，实测 Vulkan 与 CUDA 在同卡上**只差约 1%**
  （11 秒音频、small 模型：CUDA 0.84s / Vulkan 0.82s），
  所以它不是「为了跨厂商而牺牲性能」。
- 问题**纯粹在于它多引入了一个可以失败的前提**。

本文不反对将来支持 GPU，反对的是**把它变成必需**。

## 4. 关键发现：whisper 在纯 CPU 上不可行

### 4.1 问题的来源

`DESIGN.md` §4.2 的双引擎分工（小 Vosk 做唤醒/预览 + whisper 做转写精化）
由 Step 0 的数据推导而来（`DESIGN.md` 附录 B.2）：Vosk 小模型 CER 17% 不足以直接转写，
而 whisper 准确率更高且原生带标点。**这个推导没有问题，但它只在「准确率」这个维度上做过比较。**

Step 0 **没有测的维度**是：whisper 在纯 CPU 上到底多慢。

### 4.2 实测数据与推算

**【实测·外部】whisper.cpp 官方 `jfk.wav`（11 秒音频），Windows，8 线程，best of 2：**

| 模型 | 纯 CPU 耗时 | 实时倍率 | CUDA | Vulkan |
|---|---|---|---|---|
| tiny | 1.98s | 5.6x | 0.32s | 0.31s |
| base | 4.54s | 2.4x | 0.41s | 0.42s |
| **small** | **20.4s** | **0.5x** | 0.84s | 0.82s |
| medium | 73.6s | 0.1x | 1.91s | 2.02s |
| large-v3 | 133.5s | 0.1x | 3.90s | 3.73s |

> 测试机为 i9-13980HX + RTX 4090 Laptop。
> 来源：[StarWhisper Windows 基准](https://starwhisper.ai/whisper-benchmark.html)（CC BY 4.0）。

**【推算】折算到本产品目标机器 i7-12650H（6P+4E，弱于上表 i9 约 25–35%），
一段 5 秒语音的纯 CPU 精化耗时：**

| 模型 | 推算耗时 | 对「提交延迟 < 2.5s」 |
|---|---|---|
| tiny | ~1.5s | ✅ 但模型太小，中文质量存疑 |
| base | ~2.5–3s | ⚠️ 贴线，且质量未必够 |
| **small** | **~12–15s** | ❌ **差一个数量级** |
| medium 及以上 | 40s+ | ❌ 不可用 |

### 4.3 对照：SenseVoice

**【实测·外部】**

| 项 | 数据 |
|---|---|
| 架构 | **非自回归**（一遍前向出全部文字），这是速度差的根本原因 |
| 纯 CPU 实时倍率 | **RTF ≈ 0.109～0.110**（12.744 秒音频 → 1.392～1.396 秒） |
| 5 秒音频推算耗时 | **约 0.5 秒** |
| 标点 | 原生支持：设 `use_itn=1` 输出标点，样例 `"开放时间早上9点至下午5点。"` |

> 来源：[sherpa-onnx SenseVoice 预训练模型页](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)。
> **口径校正**：上表为 Mac 实测；同页另有 RK3588 嵌入式 CPU 数据
> （Cortex-A76 单线程 0.099 / 三线程 0.049；Cortex-A55 单线程 0.436）。
> **x86 桌面 CPU 应更快，但必须本地复测确认**（§6）。

### 4.4 结论

> **纯 CPU + whisper-small 达到 `DESIGN.md` §6 的提交延迟目标，不是「紧」，是数学上不可能。**
> 而 SenseVoice 在纯 CPU 上比它快**一个数量级**（约 15 秒 → 约 0.5 秒）。

这直接决定了 §1.1 的架构选择：**问题出在精化引擎，就只换精化引擎。**

### 4.5 一个附带收益

精化之所以存在，是因为预览引擎（小 Vosk，CER 17%）不够准，所以段末要重跑一遍。
换成 SenseVoice 后，这一次重跑的代价从"约 15 秒"降到"约 0.5 秒"，
`TextRefiner`（`DESIGN.md` §3.4）从"段末必须做一次慢推理"变成"一次代价很小的复核"——
**接口位置不变，只是实现更轻**。

## 6. 精化引擎验证实验

**目的**：验证 SenseVoice 能否胜任**精化**角色，并为 `DESIGN.md` 回填数值指标。

**性质**：架构不依赖此实验（§1.1 已定）。本实验是为了**落地准备 + 数值回填**，
以及**尽早暴露回退风险**（§6.6）。

**成本**：约半天。**不写 Java 代码**——两个引擎均提供 Windows 预编译二进制，
本实验全程在命令行完成。

### 6.1 原则

1. **只测精化角色。** 不需要测流式能力、不需要测唤醒词、不需要测预览——
   那些由小 Vosk 承担，且已由 Step 0 与 demo 验证。
2. **同一段音频跑所有配置**，避免用不同音频比较。
3. **所有数字记原始值**，便于事后复算与回填 `DESIGN.md` §6。
4. **测试语料用日常口述**。⚠️ **不要为专业术语设指标**——
   `DESIGN.md` §3.2「明确不做」第一条即「热词表」，§3.3 将其置于阶段二。
   在 MVP 阶段以术语正确率作为门槛是**范围外要求**。

### 6.2 步骤 1：准备测试集

- 录 **6–8 段**中文语音，每段 **5–15 秒**。
- 内容覆盖三类：① 日常口述；② 含数字与英文混说（用于检验 ITN 的改字行为）；③ 口语化、有重复与自我修正的句子（真实听写的典型形态）。
- 每段配一份**人工参考文本**（用于算 CER 与比对差异）。
- 保存为 **16kHz / 16bit / 单声道 wav**——这是所有候选引擎的共同输入格式。

### 6.3 步骤 2：执行与记录

对每段音频、每个配置，记录：

| 指标 | 说明 |
|---|---|
| **纯 CPU 耗时（秒）** | 单段推理的墙钟时间 |
| **RTF** | 耗时 / 音频时长 |
| **输出文本** | 原文照抄，用于人工比对 |
| **CER** | 与参考文本比对（可用一次性脚本算，不进仓库） |
| **标点质量** | 有无标点 / 是否正确成句 |
| **ITN 是否改错字** | 数字与英文是否被规整成错误内容（英文样例曾出现 `gold` → `code`） |
| **相比 Vosk 预览是否真的更好** | 精化的意义所在——**这是最关键的验证项**，见下 |
| **音频含首尾静音时的表现** | 段落音频由 Vosk 判定起止，天然带静音；确认模型不被静音干扰、不产生幻听 |
| **是否会把唤醒词「子曰」转进正文** | **正确性风险**：段落音频以唤醒词开头，若被转出则文字会多出「子曰」。若会，需在精化前裁掉唤醒词对应的音频段 |

**「相比 Vosk 预览是否真的更好」要专门验证**：
`DESIGN.md` §8 记录了"预览与最终文本不一致"的现象，demo README 举了
`这个需球 → 这个需求` 这个例子（流式引擎会把已吐出的字改回来）。
**SenseVoice 能否同样纠正这类错误，是它能否顶上 whisper 的核心判据**——
如果它纠不了，精化这一步就白做了。

**线程数要记录三档**（1 / 4 / 默认）：它与 `DESIGN.md` §6 的「空闲 CPU < 2%」
直接冲突（推理时必然占满多核），是 §7 第 7 项「转写中 CPU 预算」的依据。

### 6.4 结果记录表（实验时填写）

```

──────────────────────────────────────────────────────────────────────────────────

```

### 6.5 判读规则（事先定好，避免事后找理由）

| # | 条件 | 结论 |
|---|---|---|
| 1 | **CER 达标** 且 **纯 CPU 单段 < 1s** 且 **能纠正 Vosk 的明显错误** | ✅ **SenseVoice 顶替成功**，方案 C 落地 |
| 2 | CER 达标、速度达标，但**纠正能力不足**（精化后并不比 Vosk 预览好） | ⚠️ 精化这一步失去意义 → 需重新评估：是否保留精化，或换精化模型 |
| 3 | 速度达标但 **CER 不达标** | ⚠️ 换 SenseVoice 的其它量化/模型版本再试；仍不行则考虑方案 A + 核显（破红线，见 §3） |
| 4 | 速度不达标 | ⚠️ 与 §4.3 的推算不符，需重新核算整体预算，可能回到 whisper + 核显 |

**判定「达标」的具体阈值，在实验开始前确认并写死**（避免结果出来后再调标准）。建议初值：

- **CER < 10%**（对照：小 Vosk 为 17.15%，因此 10% 是有意义的门槛）
- **纯 CPU 单段耗时 < 1 秒**（5–15 秒音频；这样「提交延迟 < 2.5s」才守得住）

### 6.6 若验证不通过的回退路径

| 情况 | 回退 |
|---|---|
| SenseVoice 质量不够 | ① 换更大/不同量化的 SenseVoice 版本 ② 评估 onnxruntime 系其它中文离线模型 ③ **回退 whisper + 核显**（需重新评估 §3.1 红线，并说明为何放宽） |
| SenseVoice 速度不达标 | 与 §4.3 推算不符，重新核算预算；可能需回到 whisper + 核显 |

**注意**：回退到 whisper 意味着**必须开核显**（§4.2），即**推翻 §3.1 的红线**。
这是一个明确的代价，应在回退时显式记录决定，而不是默默放宽标准。

## 附录 A：本方案引用的数据来源与口径

**原则：每条数据标注「实测」或「推算」，并给出测试条件，便于事后复算。**

### A.1 whisper.cpp 各模型速度（实测·外部）

- 条件：Windows，`whisper-cli`，8 线程，输入为标准 11.0 秒 `jfk.wav`，每配置取两次最优
- 硬件：Intel Core i9-13980HX + RTX 4090 Laptop，32GB RAM，Windows 11
- 口径：耗时含推理，排除一次性的模型加载；RTF = 音频时长 / 处理耗时
- 来源：[StarWhisper Windows 基准](https://starwhisper.ai/whisper-benchmark.html)（CC BY 4.0）
- **注意**：该文自述「是速度测量，不是准确率排名」

### A.2 SenseVoice 速度（实测·外部）

- 条件：`sherpa-onnx-offline`，`--num-threads=1`，int8 量化模型
- 实测样例：12.744 秒音频 → 1.392～1.396 秒，**RTF ≈ 0.109～0.110**；
  含 ITN（`--sense-voice-use-itn=1`）时耗时基本相同
- 来源：[sherpa-onnx SenseVoice 预训练模型页](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)
- **口径校正**：上表为 **Mac** 实测；同页另有 **RK3588 嵌入式 CPU** 数据
  （Cortex-A76 单线程 0.099 / 双线程 0.065 / 三线程 0.049；
  Cortex-A55 单线程 0.436）。**x86 桌面 CPU 会明显更快，但需本地复测确认**
- 标点能力：官方写明设 `use_itn=1` 输出标点；样例输出
  `"开放时间早上9点至下午5点。"`（含数字规整）
- **已知副作用**：ITN 会**改字**（不只是加标点）。官方英文样例中
  `fifty pieces of gold` 被规整为 `50 pieces of code`——**这是需验证的风险点**

### A.3 GPU 与 CPU 的差距（实测·外部）

- Vulkan vs CUDA：同卡同模型**差距约 1%**（small：0.82s vs 0.84s）
- iGPU 的 Vulkan 收益：官方口径宣传「12x」，**但那是原始吞吐口径**；
  实测机为 Ryzen 7 6800H 与 Core Ultra 7 155H，
  **真实 RTF 提升为 3–4 倍**；CPU-only 基线 RTF ≈ 0.3
- 来源：[LavX 关于 whisper.cpp 1.8.3 的报道](https://news.lavx.hu/article/whisper-cpp-1-8-3-unlocks-12x-speedup-for-speech-recognition-on-integrated-amd-and-intel-gpus)
- **注意**：两处 iGPU 数据均**不是**本产品的目标机器，不可直接套用

### A.4 i7-12650H 折算（推算）

- 基准：A.1 的 i9-13980HX（第 13 代，更多核心与更高频率）
- 折算幅度：**-25% ~ -35%**（凭规格粗略估计，**必须实测替换**）
- 用途：仅用于说明数量级（本文 §4.2 的结论是「差一个数量级」，
  在这个量级的差距面前，折算误差不影响结论）

### A.5 尚未实测、需由 §6 补齐的项

| 项 | 当前状态 |
|---|---|
| 目标机器上的真实 RTF | ❌ 未测（A.4 只是推算） |
| SenseVoice 中文准确率 / CER | ❌ 未测（官方页未提供中文 CER 数字） |
| SenseVoice 能否纠正 Vosk 的明显错误 | ❌ 未测（**这是精化是否有意义的判据，见 §6.3**） |
| ITN 在中文场景下的改字是否可接受 | ❌ 未测（A.2 有英文的反例） |
| 段落音频含首尾静音时的表现 | ❌ 未测 |
| 是否会把唤醒词转进正文 | ❌ 未测 |
| SenseVoice 的 Java 绑定（JNI）与 Windows x64 预编译产物 | ✅ **已确认：不可直接依赖**（`docs/ENGINE-EXPERIMENT.md` §2）。sherpa-onnx 无 Maven Central 产物，官方 Java 绑定需自行用 MSVC + CMake 构建 JNI 动态库——与 §3.1「零环境依赖」红线冲突。模型本身可下载（int8 239MB，hf-mirror 实测可达） |

> ✅ **最后一项已确认，结论是「按原样落不了地」**：原判断「若不可用，方案 C 的集成成本会显著上升」
> 是正确的预警，实际情况比它更硬——**没有可直接依赖的产物**，不是成本上升而是需要换一条路。
>
> **已采取的处置**（详见 `docs/ENGINE-EXPERIMENT.md` §4）：
> ① `TextRefiner` 接口与所有调用路径**保持不变**（§5.1「替换点只有一处」被代码结构证明）；
> ② 精化位由 `TextRefiners.VoskOffline`（Vosk 整段离线重跑）顶替，实测 **RTF 0.241**
> （5 秒音频约 1.2s），仍守住 `DESIGN.md` §6 的「提交延迟 < 2.5s」，
> **因此不需要破 §3.1 的「不依赖核显」红线**；
> ③ SenseVoice 的两条落地路径已列出：改用 **onnxruntime（Maven Central 有，含 Windows x64 原生库）
> 自写 SenseVoice 前处理与解码**（推荐，符合零环境依赖），或自编译 sherpa-onnx JNI（不推荐）。
