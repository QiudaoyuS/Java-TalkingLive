## P1｜注入可靠性：会丢字、会误发消息

> 这一组是"用户看不见的损失"：文字没打进去、或者打进了别的程序，
> 而程序报告成功。注入是本产品**唯一的出口**，出口不诚实，前面做得再准也没用。

### 1.1 「部分注入」被当成成功（丢字是静默的）

- **位置**：`WindowsTextInjector.sendUnicode()` —— 某个字符的事件只写进去一部分时
  只打了 `log.error`，返回值仍是**已写入的正数**；`inject()` 只在 `n < 0`
  （一个事件都没写进去）时才报失败；`App.doInject` 拿到 `ok` 就
  `s.appendInjected(plan.text())`。
- **后果**：用户丢字却收到"成功"，诊断页里没有任何记录；而且会话状态以为整段都落地了，
  与实际不符。`WholeSegmentPolicy` 下一次按 `codePointCount(already)` 算退格数时，
  会按**不存在的字数**退格。
- **修法**：把"期望事件数 / 期望码点数"与"实际写入数"一起放进 `TextInjector.Result`，
  不匹配即 `ok = false`，并提示「只写入了 X/Y 个字」。
- **成本**：小。

### 1.2 注入途中不复核前台窗口（TOCTOU）

- **位置**：`WindowsTextInjector.inject()` 只在**开始前**比对一次 `GetForegroundWindow`；
  之后逐字符 `SendInput`，每字 `sleep(charGapMillis)`（默认 20ms）。
- **后果**：30 字 ≈ 600ms 以上的注入期内，只要 Alt+Tab、弹通知、UAC 抢焦点，
  **后半段就打到别的窗口**，而 `Result` 仍是 ok。用户看到的是"打了一半、另一半不见了"。
- **修法**：焦点还原之后再复核一次，并在每 N 个字符（或每次 sleep 后）复核
  `GetForegroundWindow == expectedWindow`，不符即中止并如实报告。
- **成本**：中。
- **备注**：自动发送这一侧已经由 `StateMachine.autoSendAllowed` 拦住"提交时前台已变"，
  但 `WindowsTextInjector.press()` 自身仍然没有任何前台校验（见 1.3）。

### 1.3 `press()` 自身零校验（自动发送的最后一米）

- **位置**：`WindowsTextInjector.press(KeyCombo)` 直接 `send(keys)`，不看前台、不看状态。
- **后果**：目前唯一的调用点（`App.doInject`）已经在调用前用 `autoSendAllowed` 判过，
  所以**当前不可达**；但把安全前提放在调用方，任何新的调用点都会绕过它。
  而一个回车落在聊天工具里是**不可挽回**的（消息会被直接发出去）。
- **修法**：把"目标是否仍是前台"作为 `press()` 的前置校验，或改成
  `press(combo, expectedWindow)`。
- **成本**：小。

### 1.4 注入期间不检测修饰键状态

- **位置**：`Win32.User32.GetAsyncKeyState` 已声明（0.9.2 起被 `EscapeWatcher` 用来读 Esc），
  但注入路径不检查 Ctrl / Shift / Alt / Win。
- **后果**：用户按住 Ctrl（或上一次事件把 Ctrl 卡在按下态）时，
  `KEYEVENTF_UNICODE` 事件会被目标按"修饰键 + 虚拟键"解释，文字变成快捷键；
  自动发送会把 Enter 变成 Ctrl+Enter。
  SendInput 会如实报告"写入成功"，所以**重试救不了**。
- **修法**：注入前检查修饰键，按下则等待或中止并明确提示（不要自己补发 keyup）。
- **成本**：小。

### 1.5 注入的「落地真值」缺失（SendInput 报成功 ≠ 落地）

- **位置**：`AppConfig.charGapMillis` 的注释里已经记录了实测故障：
  **14 个事件全部写入成功，而微信输入框里只有 2 个字**。
- **后果**：注入成功率这个最关键的指标**目前无法度量**，`charGapMillis` 只能靠手感调。
- **修法**（按投入从小到大）：
  1. 纯逻辑单测：把 `sendUnicode()` 的"文本 → 事件序列"抽成纯函数（或抽出 `InputSink`），
     断言每个码点的 down/up 顺序、代理对是 4 个事件、部分写入后**不产生孤立代理**；
  2. `--inject-target` 测试窗口：标准 `JTextField` 记录**真实收到的字符序列**，
     注入后比对期望/实收 —— 这是唯一可自动化的真值来源，也是把 `charGapMillis`
     量化为"丢字率曲线"的唯一办法；
  3. 外部程序用 UI Automation 读回文本后 diff（记事本 / 浏览器地址栏 / VS Code）；
  4. 微信 / QQ 这类自绘输入框只能半自动：注入带校验和的随机串 → 提示用户 Ctrl+A/Ctrl+C
     → 读剪贴板逐码点 diff，报告"从第几个字开始缺"。建议做成设置窗口里的一个按钮。
- **成本**：中（第 1、2 项先做，收益最大）。

### 1.6 `charGapMillis` 允许 0，而 0 是已知的故障值

- **位置**：`AppConfig.MIN_CHAR_GAP_MILLIS = 0`；而
  `TextInjectorLayoutTest` 的断言消息里自己写着"默认为 0 会让微信这类自绘输入框丢字"。
- **后果**：用户把间隔拖到 0 就复现"只出现第一个字"，而且没有任何提示。
- **修法**：下限提到 5–10ms，或在界面上把 0 标注为"可能丢字"。
- **成本**：一行。

### 1.7 控制字符没有过滤

- **位置**：`sendUnicode()` 不区分内容，逐码点发送。
- **后果**：识别结果里若出现 `\n` / `\t`，会被当按键送进目标 ——
  在聊天工具里就是"话还没说完就发出去了"。
- **修法**：注入前过滤或转换控制字符（`TextUtils` 里已有清理工具，需确认覆盖范围）。
- **成本**：小。

## P2｜悬浮球可用性：它是唯一入口

> 托盘入口已移除（1.11），产品**没有**别的界面入口。所以"球点不到"等于"产品不可用"。

### 2.1 贴边收起状态下，单击球**什么都不会发生**

- **位置**：`FloatingBall.mousePressed()` 先 `revealNow()`（启动滑出动画），**之后**才记录
  `pressPoint`；而滑出会让窗口在静止的光标下平移 48px；`mouseReleased()` 用
  `e.getPoint().distance(pressPoint) < 5` 判定点击。
- **后果**：松手时坐标已相对**新**窗口位置，差 ≥48px（哪怕只过一帧也已 11px），
  于是 `wasClick` 对任何真实点击**恒为 false** → 不走 `onLeftClick()`，而走 `maybeDock()`
  → 判定仍该贴边 → 收回 → 150ms 轮询发现鼠标还在 → 再滑出。
  **净效果：弹出 → 缩回 → 再弹出，什么都没发生**，而"球被收起"正是最需要
  "点一下就说话"的状态。
- **修法**：点击判定改用屏幕坐标（`e.getLocationOnScreen()` 存/比）；
  或收起状态下按下不启动动画，判定为点击后再 reveal + 开始听写。
- **成本**：小。

### 2.2 边界计算用的是**单屏**矩形，而项目自己写好的虚拟屏幕实现没人用

- **位置**：`FloatingBall` 里七处 `getGraphicsConfiguration().getBounds()`
  （夹紧 / 默认位置 / 贴边判定 / hiddenX / revealedX）与 `PreviewBar.reposition()`；
  而 `DpiScale.virtualBounds()` / `clampToScreen()` **只被 `SelfTest` 与 `DpiProbe` 引用**。
- **后果**（都在多显示器下）：
  - 保存过位置的球在重启时会被"夹回"主屏（窗口尚未定位时取到的是默认屏的 GC）；
  - 跨屏拖动会被卡在当前屏边缘；
  - 预览条的边缘翻转会算到别的屏上去；
  - **任务栏可用区没算**（全仓库无 `getScreenInsets`），球可能被拖到任务栏下方而完全点不到；
  - **运行期拔屏 / 改分辨率不会重新夹紧**（无 `DisplayChange` 监听），球可能永久停在屏幕外。
- **修法**：边界一律改用 `DpiScale.clampToScreen/virtualBounds` + `Toolkit.getScreenInsets`；
  `PreviewBar` 改成显示之后再 `reposition()`；加一个低频的"位置仍在可见区域内"检查。
  另外自检 H 用虚拟边界断言，**永远抓不到**这个偏差，断言也要跟着改成对生产代码的调用。
- **成本**：中。

### 2.3 球被遮住 / 找不到时，用户没有出口

- **位置**：右键菜单只有 手动开始·结束 / 暂停 / 设置 / 查看日志 / 退出；
  没有"临时隐藏"、没有"重置位置"；全局热键在 §3.2 被列为"不做"。
- **后果**：全屏程序遮挡 + 麦克风故障 = 用户**完全没有入口**，只能杀进程；
  而单实例锁还会在重启时告诉他"已经在运行了"。
- **修法**：菜单加「临时隐藏 30 分钟」与「重置到屏幕中央」；
  并重新评估 §3.2 的"不做全局热键"（`RegisterHotKey` 约 30 行，
  能同时解决"球被遮住"和"想一键暂停"两件事）。
- **成本**：小。

### 2.4 右键菜单是构建时缓存的，文案与可点状态会过期

- **位置**：`FloatingBall` 的菜单只构建一次并缓存（`ballMenu` 从不失效）。
- **后果**：暂停后菜单仍写"暂停监听"；"手动开始 / 结束听写"仍可点但被状态机忽略 ——
  界面状态与实际状态不一致，正是"改了没反应"的老套路。
- **修法**：弹出前重建，或注册 `PopupMenuListener` 在 `popupMenuWillBecomeVisible` 里刷新
  文案与 `setEnabled`。
- **成本**：小。

### 2.5 悬浮球尺寸与字号不随 DPI 缩放

- **位置**：`Theme.BALL_WINDOW / BALL_DIAMETER` 是写死的像素，`PEEK`、`DOCK_THRESHOLD`、
  `MIC_ICON_SIZE` 同样；而字体全部乘了 `Theme.dpiScale()`。
- **后果**：200% 缩放下球只有 34 逻辑 px，明显偏小；且 `dpiScale()` 取的是
  `Toolkit.getScreenResolution()`（**主屏** DPI 的单一值），混屏时副屏必错。
- **修法**：几何量也走缩放；DPI 改按窗口所在显示器取（`DpiScale.dpiForWindow` 已有）。
- **成本**：小。

## P3｜转写质量与验收：通向 1.0

> 0.9 的定位是"功能完成、验收未完成"。这一组是把它推过 1.0 线的东西。

### 3.1 精化引擎（SenseVoice）仍然没落地

- **位置**：`App.createRefiner()` 是**唯一替换点**（接口 `TextRefiner` 与所有调用路径都不用改）。
  当前装的是 `TextRefiners.VoskOffline`（Vosk 整段离线重跑），并在界面/日志里
  **如实标注为"非 SenseVoice"**。
- **卡在哪**：sherpa-onnx 没有 Maven Central 的 Java 绑定，也没有 Windows x64 预编译产物
  （`docs/ENGINE-EXPERIMENT.md` §2 已确认）。**模型本身可下载**（int8 239MB）。
- **两条落地路径**（详见 `ENGINE-EXPERIMENT.md` §4）：
  1. **改用 `com.microsoft.onnxruntime:onnxruntime`（Maven Central 有，含 Windows x64 原生库）
     自写前处理与解码** —— 推荐，符合"零环境依赖"红线；
  2. 自编译 sherpa-onnx JNI —— 不推荐（要求用户装 MSVC + CMake）。
- **建议的第一步（便宜且能定生死）**：先用 **Python 版 sherpa-onnx**（有官方 Windows wheel）
  跑一遍中文 CER / 标点 / ITN 的实测。这些数`ENGINE-EXPERIMENT.md` §5 至今标着"未测"，
  而它们决定"自写 Java 解码"值不值得投入 —— 不要先写 Java 再验证效果。
- **成本**：Python 验证小；Java 落地中～大。

### 3.2 把 §9.3 的手工验收自动化（`--replay` 回放）

- **位置**：`App.injectAudioForTest(byte[])` **已经存在**，注释写着"供自检在无麦克风环境下
  驱动完整流程"，但**全仓库没有任何调用点**。整条链路唯一的下游契约是
  `AudioCapture.Listener.onPcm(pcm, rms)`，接口天然成缝。
- **为什么做得到**：`SilenceDetector.accept(rms, frameSeconds)` 按**帧时长**累计、不看墙钟 ——
  回放可以快于实时，结果确定可复现。
- **收益**：`DESIGN.md` §9.3 里"需要真人"的三条大部分可以变成一条命令：
  | §9.3 条目 | 自动化做法 |
  |---|---|
  | 唤醒命中率 ≥ 9/10 | 录 10 段唤醒语料，回放统计命中数 |
  | 10 分钟误唤醒 = 0 | 播一段播客音频，统计误命中 |
  | 真实语音 CER | 每段 wav 配同名 `.txt` 参考文本，复用 `EngineBench` 入口自动算 CER |
- **修法**：把它升级成正式的 `--replay <wav|目录>` 子命令（读 16k 单声道 WAV → 逐帧喂
  `CaptureBridge`），并把这三种测量各写一个脚本入口。
- **成本**：中。**这是把 0.9 推向 1.0 最直接的一步。**

### 3.3 没有 CI，也没有"一条命令验证"

- **位置**：无 `.github/`；`AGENTS.md` 要求"交付前确保所有测试和验证全部通过"，
  但目前要人工记得跑 6 条命令（`mvnw test` / `--doctor` / `--self-check` /
  `EngineBench` / `EngineSmoke` / `SampleInjector`）。
- **修法**：加一个 `verify.cmd`：`mvnw -q test` → `--doctor` → 断言报告里 0 失败 →
  退出码非 0 就拦。自用工具不需要 GitHub Actions，一条脚本收益最大。
- **成本**：小。

## P4｜产品体验决策（需要拍板或先实测）

### 4.1 「精化」这一步还有没有价值？

- **依据**：`ENGINE-EXPERIMENT.md` §4.5 的实测——预览与精化**错得一样**（差异 0–4 码点），
  因为两者基于**同一个模型**；而 15 秒段落要 7.3 秒，超出 §6 的"提交延迟 < 2.5s"。
  1.7 之后预览 / 落字 / 精化已经统一到同一个模型，"段末重跑一遍"的收益必须被证明。
- **修法**：用一整天实际使用 A/B —— `--refiner none` 早已实现（走
  `TextRefiner.Result.fallback(previewText)`，延迟归零）。若离线重跑并不明显更准，
  就把它降级为可选，换来的是提交延迟预算彻底守住、长段落不再超时。
- **成本**：一天实测。**是当前性价比最高的产品决策。**

### 4.2 静音阈值写死 0.012，而本机实测本底噪声是 0.0107

- **位置**：`SilenceDetector.DEFAULT_THRESHOLD`；`App` 永远使用它（构造器支持传值，但没人传）。
- **后果**：环境稍吵（或麦克风增益偏高）时，静音计时会被噪声不断重置，
  **段落不再因静音自动结束**。`IMPLEMENTATION-STATUS.md` §3.4 已记录这条。
- **修法**：启动健康检查**已经**测了本底 RMS，直接拿它做自适应
  （例如 `threshold = max(0.012, noise * 2.5)`），或把阈值变成配置项。
  注意 `WakeGate` 用的是 0.010，两者耦合，要一起看。
- **成本**：小（约 20 行）。

### 4.3 大模型常驻 2.4GB / 冷启动 17–21 秒

- **位置**：`AppPaths.asrModelDir()` 的"装了大模型就自动用"策略；`DESIGN.md` §6 的
  "空闲内存 < 500MB"预算在装大模型时**已经不成立**（如实记录在 `ENGINE-EXPERIMENT.md`）。
- **后果**：与"常驻后台"的产品定位冲突；8GB 内存的机器会很难受。
- **修法**（可组合）：
  1. 启动时读物理内存，低于阈值明确降级到小模型并在诊断页写明原因；
  2. `LoadingWindow` 加阶段文案与已等待秒数（等待不可怕，不知道为什么在等才可怕）；
  3. 重新评估"预览用小模型即时出字，大模型就绪后整体替换为更准文本"这个折中
     —— 它能把冷启动从 21 秒拉回 3 秒，代价是预览会"变一次"。
- **成本**：中。

### 4.4 被丢弃的段落无法找回

- **位置**：`DESIGN.md` §12 #1 至今未决。切窗口已经改成照常提交了，
  但 Esc / 暂停 / 采集中断 / 单段上限截断仍然会把一整段话扔掉。
- **修法**：加**内存内最近 N 段**（不落盘、不违反"不做历史记录"）+ 悬浮球右键
  「插入上一段」。把"不可挽回的损失"变成"再点一下"。
- **成本**：小。

### 4.5 注入之后无法纠错

- **位置**：识别错了，用户只能自己删。
- **修法**：右键菜单加「撤回上次注入」（发送等量退格；`TextUtils` 已有码点工具）。
- **成本**：小。

### 4.6 首次运行体验：模型要用户自己跑 PowerShell 下载 1.3GB

- **位置**：`README.md` / `DESIGN.md` 附录 D 的下载步骤；`DESIGN.md` §12 #3 未决。
- **修法**：检测缺模型 → 一键下载（带进度、hf-mirror 优先）→ 解压 → 提示。
  这是从"自用工具"走向"能给别人用"的第一道坎。
- **成本**：中。

### 4.7 预览条：定位时机、高度无上限、25Hz 全量重排

- **位置**：`PreviewBar.render()` 里 `pack()` + `reposition()` 都发生在 `setVisible(true)`
  **之前**（首次显示时拿到的是默认屏的 GC）；文本高度没有上限；每帧
  （`AudioCapture` 按 `sampleRate/25` 读，约 40ms 一帧）都会重排并重建 HTML，
  **即使文本没变**。
- **后果**：预览条可能跑到别的屏；60 秒长段落能长出几百像素高的白板，
  盖住用户正在写入的输入框；文字未变时也在做无用的重排与抖动。
- **修法**：显示之后再定位；文本/状态/锚点未变则直接返回；高度设上限（或内部滚动）。
- **成本**：小～中。

## P5｜工程卫生（可批量清扫）

| # | 问题 | 位置 | 成本 |
|---|---|---|---|
| 5.1 | **上帝类**：`App.java` 约 2200 行 / 45+ 方法，一个类里同时有音频线程热路径、EDT UI、CLI 三种模式、装配与诊断 | 建议新建 `com.talkinglive.app` 包承载编排层（受 `ArchitectureTest` 约束，**不能塞回 `core`**）：`DictationPipeline` / `EngineBootstrap` / `ConfigController` / `AppLifecycle` / `StatusReporter`；`SelfTest`（约 1480 行）按 关注点 三分；`SettingsWindow`（约 947 行）里的 CJK 折行算法（约 180 行纯函数）最值得先抽出来 | 中 |
| 5.2 | **诊断窗口的「重新自检」在 EDT 上跑整套 `SelfTest`** | 违反 `SelfTest` 自己写的前提（"绝不能在 EDT 上跑"）：会冻结窗口数秒，并在真实桌面上**再造一颗悬浮球、用 Robot 移动鼠标**，结论本身也失真。改为后台线程 + `onUi` 回填 | 小 |
| 5.3 | **资源泄漏** | `diagnostics` 窗口从不 dispose、日志订阅无人 close；`FloatingBall` 没有 `dispose()` 覆写，构造函数里启动的 33ms `levelTimer` 永不停（每跑一次自检多一个 30fps 计时器）；`singleInstanceLock` 从不 close；`notices` 无界增长；`ForegroundWatcher.ignored` 只增不减 | 小 |
| 5.4 | **`paused` 仍是三份状态** | `App.paused` / `ball.setPaused(...)`（视觉）/ `StateMachine.paused` 各自漂移；0.9.4 只修掉了"麦克风恢复时静默解除用户暂停"这一处症状。建议收敛成一个来源 | 小 |
| 5.5 | **`AudioCapture.close()` 与 `loop()` 竞态** | 可能在 `closing` 置真之后仍打开设备，而那个设备再也没人关；且 `closing` 不复位 → 对象是一次性的 | 小 |
| 5.6 | **`DpiScale.initProcessAwareness()` 把失败缓存成成功** | 失败路径也置 `awarenessSet = true`，于是"第一次返回 false、第二次返回 true"。而进程实际"不感知 DPI"时仍按物理像素换算 → 坐标被推出屏幕 | 一行 |
| 5.7 | **拖动悬浮球松手时在 EDT 上同步落盘** | `FloatingBall` 的几何回调直接 `persistConfig()` | 小 |
| 5.8 | **手改 `config.json` 会被静默回滚**（无热重载） | 配置只在启动时读一次；任何一次 `persistConfig` 都会把内存里的整份写回，手加的键/手改的值一律丢失。而"注入间隔 / 单段上限 / 热词"界面上没有入口，页脚只写着"改 config.json" —— 用户照做就被覆盖。要么加高级折叠区，要么在页脚写明"改完需重启，运行中修改会被覆盖" | 小 |
| 5.9 | **非法配置 = 起不来，且没有自愈** | 已存在的坏配置直接抛异常，`--settings` 也救不了（配置在 UI 启动之前就读了）；不坏文件、不备份、无版本号字段可用于迁移。升级时一旦收紧取值范围，用户就只能手改 JSON | 小 |
| 5.10 | **静音下拉框条目会累积** | 对手改的列表外取值（例如 `silenceSeconds = 7`），每次 `setVisible(true)` 都 `addItem` 一次 → 每打开一次设置窗口多一条 | 小 |
| 5.11 | **`dockEnabled` 是半死开关** | 只有一处读它，界面无入口，而 `maybeDock()` 完全不看它 → 手改成 `false` 后贴边照常发生。正是本文档反对的"改了没反应的开关" | 小 |
| 5.12 | **`IMPLEMENTATION-STATUS.md` 里的测试数字会再次过期** | 它写死了"246 项单测 + 44 项自检"，而 0.9.4 时已是 415 / 71。建议改成"见 `mvnw test` 输出"，不写常量 —— 与自检 F4"断言直接数组件、不写死常量"是同一个道理 | 一行 |
| 5.13 | **`.gitignore` 的注释与自身规则矛盾** | 注释说"Maven wrapper 本体随仓库提交"，下一行却排除了 `.mvn/wrapper/*.jar`（实际未提交）→ 首次构建必须联网 | 一行 |
| 5.14 | **`Win32.java` 的注释与实现矛盾** | 注释写"KEYBDINPUT 实际落在偏移 32"，而实现与测试用的是 8 / 10。**照注释改代码就会重新引入"INPUT 结构体少 8 字节、字符全写丢"那个已经修过的缺陷** —— 这条注释必须改掉 | 一行 |
| 5.15 | **`--allow-multiple` 下两个实例会并发写同一份 `config.json`** | 临时文件名固定且无写锁 | 小 |
