> 版本 0.1 ｜ 状态：**台账，只增不改**

## 这份文档怎么用

- **只记"已经不再讨论"的事**。PENDING-ISSUES 里对应的条目在决策落地后**删掉并指向本文件**，
  免得同一件事在两处各写一份、然后各自漂移。
- 每条必须写 **结论 / 理由 / 代价 / 复核条件**。没有复核条件的决策会变成信仰。
- **只增不改**：结论变了就追加一行，并注明"取代 Dx"，原行保留 —— 追溯比整洁值钱。
- 决策的**依据**尽量是实测数据，并写清口径（同一件事按不同口径可以差一个数量级，
  本仓库在"内存占用"上就栽过一次：堆内 3MB 与进程工作集 3.6GB 是同一次运行）。

## D0｜接受大模型带来的冷启动代价（2026-09-19，用户拍板）

- **结论**：正常启动时**同步加载大模型**，代价是"球出现"要等约 18 秒，用户接受。
- **理由**：小模型的错误率太高 —— CER 17.15% 对 7.43%；更硬的一条是**小模型词表里没有任何英文**
  （`A–Z`、`AI`、`APP`、`CPU`、`PDF` 全部 `find_word` 返回 -1），而本产品的典型用法正是
  AI 对话、写代码、发技术消息。
- **代价**：启动从约 2 秒变成约 18 秒（实测：模型加载 16,102ms / 16,701ms，到"启动完成"约 18.4 秒）。
  期间只有 `LoadingWindow` 可见。
- **复核条件**：跑 `DESIGN.md` §9.3 那 10 段真实听写时，顺便确认"大模型在你的真实场景里是不是明显更准"。
  若并无明显改善，这 18 秒就不划算 —— 决策可复查，而不是变成信仰。

## D1｜2.4GB 内存：接受，但给用户一条自己说了算的出口（2026-09-19）

- **结论**：保留大模型常驻；**不做**"按物理内存自动降级"；新增 `AppConfig.useLargeModel`
  （默认 `true`，只在 `config.json` 里改，改完需重启）。
- **理由**：内存与启动是同源取舍，D0 既然选了准确率优先，就不该在低配机器上**悄悄**违背它 ——
  静默降级会让用户"识别忽好忽坏"却找不到原因（§7「任何失败都必须可见」）。
  给出口而不是替他决定。
- **代价**（实测，16GB 机器、启动 20 秒后稳定值，口径写在括号里）：
  **工作集约 3.6GB**（任务管理器「内存」列）、**私有提交约 4.3GB**（同窗口的「虚拟内存」/「提交大小」，
  `run.cmd` 加了 `-Xmx512m` 之后；默认 JVM 参数下约 4.6GB）；
  小模型路径是 **工作集 0.35GB / 提交 1.0–1.4GB**。
  闲置约 1 小时后工作集被系统裁剪到约 0.76GB，**但提交量不变**。
  它是**原生内存**，不在 Java 堆里（堆内仅 3MB），`-Xmx` 只能影响其中一小部分（实测省 0.36GB）。
- **顺带纠正**：此前文档写的"常驻约 2.4GB"**对不上任何一个口径**（最接近"模型加载中"那一刻的读数）。
- **复核条件**：8GB 机器上装/不装大模型各跑一组同样的日常任务，比整机响应；
  并统计一周内"实际等了那 18 秒"的次数（一周 0 次 = 代价可接受）。
  **另有一条更硬的复核线（2026-09-23 触发）**：提交量是**回收不了**的，会与游戏/大型程序
  抢系统提交额度 —— 用户实测出现过打游戏时"虚拟内存不足被强退"，见「仍在待办」里的那条。

## D2｜「出口诚实」纳入 1.0 门槛（2026-09-19）

- **结论**：`TextInjector.Result` 带上 `eventsExpected`；实收 < 期望即 `PARTIAL_WRITE` 失败，
  并提示"只写入了 X/Y 个键盘事件……已注入的内容可能不完整，请自行核对"。
  临界基准由纯函数 `TextInjector.plannedEvents(text, backspaces)` 独立算出。
- **理由**：注入是本产品**唯一的出口**。"丢字却报成功"会让用户彻底失去信任，
  而会话账本还会按**不存在的字数**算下一次退格。
- **代价**：用户会看到更多失败提示（以前是静默成功）。**并且它只解决"事件级"诚实** ——
  微信那类"事件全写成、目标程序自己吞字"仍检测不到，那需要落地真值
  （`PENDING-ISSUES` P1.5 的 `--inject-target` 测试窗口）。
- **复核条件**：真实使用时若频繁出现 `PARTIAL_WRITE`，说明 `charGapMillis` 偏小或目标程序吞字，
  按提示调大间隔再观察。

## D3｜唯一入口的兜底：两个菜单项（热键后置）（2026-09-19）

- **结论**：悬浮球右键新增「重置到屏幕中央」（顺手解除贴边）与「临时隐藏（到点自动恢复）」；
  **全局热键暂不做**（DESIGN §3.2 的"不做"仍然有效，但不再是"永不"）。
- **理由**：球是唯一入口（托盘已移除）。被全屏程序遮住 + 麦克风故障 = 用户**完全没有入口**，
  只能杀进程，而单实例锁还会在重启时告诉他"已经在运行了"。
- **代价**：菜单从 5 项变 7 项（与"克制"有摩擦）；临时隐藏期间**没有把手能把它叫回来**
  （没有全局热键），所以时长固定 30 分钟、到点自动回来，且提示条明确写着"隐藏的只是界面，
  唤醒词照常有效"—— 否则用户会以为隐藏等于退出，然后去杀进程（那正是这个菜单要避免的）。
- **复核条件**：若"临时隐藏"仍让人觉得回不来，就是该做全局热键的信号。

## D4｜开机自启：可选，默认关（2026-09-19）

- **结论**：新增 `--install-startup` / `--uninstall-startup`；**默认不开**。
  机制是**当前用户的「启动」文件夹**（写一个转交仓库 `TalkingLive.vbs` 的启动器），**不是注册表 Run 键**。
- **理由**：D0 接受了 18 秒冷启动，而产品定位是"常驻后台"——不自启意味着**每天第一次用都要等它一次**，
  而用户没有"打开它"这个心智动作（没有主窗口，球也不在），他的结论只会是"它坏了"。
  自启是用户的决定，所以默认关、由子命令显式开启。
- **为什么不用 Run 键**（实测，同一台机器同一用户）：
  `RegOpenKeyEx(Run, KEY_SET_VALUE)` 成功，而 `RegSetValueEx` 返回 **5（拒绝访问）**；
  对照 `HKCU\Software` 写入返回 0；`reg.exe` 能写是因为它是微软签名程序。
  也就是说 Run 键被安全策略保护，**未签名进程写不进去**，与代码怎么写无关。
  启动文件夹是同一个系统机制（登录时启动、每用户、免管理员），而且用户**看得见**那个文件、
  删掉即取消。
- **代价**：多一个自启入口要维护（含卸载路径）；启动文件夹里那个脚本**新建时会触发实时防护扫描**
  （实测三次跑一次被拒、失败那次多花 30 秒）→ 因此实现是"临时文件 + 原子替换 + 重试"，
  既跨过扫描窗口，又保证不会留下半个脚本（半个脚本躺在启动文件夹里 = 每次开机弹一个错误框）。
- **复核条件**：若某天安全策略也拦启动文件夹的写入，`--install-startup` 会明确报错（不静默失败），
  此时再评估换用任务计划程序或要求用户手动放置快捷方式。

## D4-修订｜**移除开机自启**（2026-09-23，取代 D4）

- **结论**：D4 实现的 `--install-startup` / `--uninstall-startup`（写当前用户的「启动」文件夹）
  **整体删除**：`system.StartupEntry`、它的测试、两个子命令与帮助文本全部移除。
  代码里只留一条注释说明"这里曾经有它、为什么拿掉"。
- **为什么改**（用户提出，成立）：大模型常驻会让本进程的**提交量达到约 4.3GB，而提交是系统
  **回收不了**的**（闲置时只裁剪工作集）。"开机静默启动"于是意味着：**你打游戏时它也在占提交额度**。
  用户实测出现过"打游戏十分钟内连续几次因虚拟内存不足被强退"（本机内存 15.7GB、
  提交上限只有约 22.4GB，游戏自己往往要 8–14GB）。
  **一个会自我启动的重内存后台程序，风险大于它带来的便利。**
- **代价**：失去"开机即在"的便利 —— 每天第一次用要手动启动，并等 16–18 秒加载模型。
  缓解：把 `run.cmd` 放个快捷方式；或改用小模型（提交降到约 1.4GB，启动约 2 秒，代价是准确率）。
- **复核条件**：**前提变了才能重新考虑** —— 即"闲置时释放模型/惰性加载"真的做出来之后
  （那时开机自启不再意味着常驻 4.3GB）。在那之前不要加回。
- **附**：D4 里那条"Run 键被安全策略保护、未签名进程写不进去"的实测结论**依然有效**
  （它是对 Windows 行为的观测，与本次回退无关），已随 D4 正文保留。

## D5｜`--doctor` 真正不碰 UI（2026-09-19）

- **结论**：`SelfTest.run(env, includeUi)` 增加开关；`--doctor` 传 `false`、`--self-check` 传 `true`；
  跳过时报告里**如实标注**"UI 段：按参数跳过"，并写明去哪验。
- **理由**：`--doctor` 承诺"环境自检后退出"，而它此前调的是完整自检 —— 桌面可用就会
  **造一颗悬浮球并用 `Robot` 真的移动鼠标**，而文档与注释都写着"不碰鼠标"。
  用户可能正在用鼠标做别的事。
- **代价**：`--doctor` 少测 20 项 UI 检查（实测 68 → 48 项），它们由 `--self-check` 覆盖，
  且在那份报告里是**明写跳过**而不是伪装通过。
- **复核条件**：无需复核 —— 这项由 `SelfTestUiGateTest` 守住（开关失效是静默的：
  界面看不出异常，只有用户鼠标被抢时才会察觉）。

## D3-修订｜删掉「临时隐藏」（2026-09-19，取代 D3 的第二个菜单项）

- **结论**：D3 里的「临时隐藏（到点自动恢复）」**整个删除**；只保留「重置到屏幕中央」。
- **为什么改**（用户当场提出的质疑，成立）：把球藏起来之后，产品**没有任何把手能把它叫回来** ——
  没有全局热键（D3 把热键后置了）、菜单在球上、第二次启动又被单实例锁挡住
  （它只会弹"已经在运行了…请先结束旧的 TalkingLive 进程"）。于是隐藏之后：
  找回球 = **只能等 30 分钟**；退出程序 = **只能杀进程**。
  这恰恰是 §7 明令禁止的「只能杀进程」状态 —— 而 D3 本来就是为了消灭这一类状态才做的，
  我在同一个改动里又造了一个。
- **我当时错在哪**：推理是"没有热键 → 藏起来就没有把手 → 那就让它到点自动回来"，
  **把"安全网"当成了"把手"**。30 分钟不是一条出路，只是一个延迟；
  而本 D3 自己写的复核条件正是："若『临时隐藏』仍让人觉得回不来，就是该做全局热键的信号"——
  该条件已触发，我选择了更保守的那条路（删掉功能），而不是顺手引入全局热键。
- **代价**：失去"我现在不想看到球"这个能力。替代品是**贴边收起**：只留一条（约 12px 球体）、
  鼠标一碰就滑出，**始终有把手**。若将来确实需要完全隐藏，必须**先有键盘把手**
  （全局热键，需要在 §3.2「不做」上重新拍板），不能只靠计时器。
- **复核条件**：若日常使用中反复出现"想把球藏起来"的诉求，说明该做的是全局热键
  （一次解决"隐藏怎么回来 / 球被遮挡 / 一键暂停"三件事），而不是再做一个没有把手的隐藏。

## A 批次｜"唯一出口 / 入口"六项缺陷修复里的四个行为决定（2026-09-19）

> 六条缺陷本身是 bug 修复（不需要拍板），但其中**四处改变了行为**，所以记在这里。
> 另两条是纯 bug：预览 partial 键名、贴边点击判定 —— 见各自代码注释与 `PENDING-ISSUES` 0.6 的删除说明。

### A-1｜注入间隔下限从 0 提到 5ms

- **结论**：`AppConfig.MIN_CHAR_GAP_MILLIS` 0 → 5；**老配置里残留的 0 在读入时被抬到下限**并记一条警告。
- **理由**：0 是**已知的丢字值**（灌太快时微信/QQ 这类自绘输入框主动丢掉后面的 `WM_CHAR`，
  而 `SendInput` 会如实报告"全部写入成功"）。一个已知会出错的取值不该留在可行域里。
- **代价**：理论上最慢的注入每字多 5ms（20 字多 100ms，可忽略）；老配置被自动修正（有日志）。
- **复核条件**：若某个目标程序上仍出现丢字，说明下限还不够，按 `PARTIAL_WRITE` 提示继续调大。

### A-2｜控制字符在注入前剔除

- **结论**：`WindowsTextInjector.inject()` 注入前过一遍 `TextUtils.withoutControlChars`。
- **理由**：`KEYEVENTF_UNICODE` 会把换行/制表**当按键**送进目标程序 —— 在聊天工具里一个换行
  就等于"把没写完的消息发出去"。
- **代价**：识别结果里真出现换行时它会被**丢掉**（而不是变成空格）。宁可少一个排版换行，
  也不冒"提前发送"的风险。**文本层刻意保留换行**（`PunctuationProcessor` 认为那可能是有意的分段），
  所以这道防线只在出口，预览仍按原样显示。
- **复核条件**：若反馈"段落里的换行没了"，说明需要的是"换行转空格"而不是"丢弃"。

### A-3｜修饰键被按住时：等一秒，仍按着就**中止注入**

- **结论**：注入前查 Ctrl/Alt/Shift/Win；按住则最多等 1 秒；仍按着 → `MODIFIER_HELD` 失败并提示。
- **理由**：按住修饰键时 Unicode 事件会被目标按"修饰键 + 虚拟键"解释 —— 文字变成快捷键
  （Ctrl+W / Ctrl+S 之类还有破坏性），而 `SendInput` 会如实报告成功，**事后无法分辨、重试救不了**。
- **代价**：这一段的文字**没有打进去**；可挽回性靠提示里带上识别到的内容
  （`showNotice` 会附上"（识别到的内容是：…）"）。选择是：宁可丢一次**可见的**落字，
  也不要触发一次**不可见的**快捷键。
- **复核条件**：若 `MODIFIER_HELD` 频繁出现（说明键盘状态卡住或判据过严），
  应改成"只在按住 Ctrl/Win 时中止，Alt/Shift 放行"。

### A-4｜自动发送前由**注入器自己**复核前台

- **结论**：新增 `TextInjector.press(combo, expectedWindow)`；Win32 实现里复核前台，
  不符即 `FOREGROUND_CHANGED` 失败。
- **理由**：调用方（`StateMachine.autoSendAllowed`）确实已经判过一次，但**任何新的调用点都会绕过它**，
  而一个回车落在聊天工具里是不可挽回的。
- **代价**：多一次 `GetForegroundWindow`（可忽略）；若判据偏严，会出现"该发却没发" ——
  那是**安全的一侧**（文字已经打进去了，用户自己按回车即可）。
- **复核条件**：若出现"开了自动发送却不发"的反馈，再核对前台比较的口径（窗口 vs 焦点控件）。
